This session is about model weight quantization

The embedding-vector case (covered in Production Optimization) is a search-side optimization. What follows is purely about shrinking the model itself so it fits on smaller hardware and runs faster.

B. The Precision Spectrum

What “bits per weight” actually means

How Numbers Are Stored

A model weight is a number. The precision says how many bits we spend representing it.

Format Bits Range Use case
FP32 32 huge, very fine Training (old default)
FP16 16 smaller, fine Training + inference (modern default)
BF16 16 wide range, coarser Training (Google TPU native)
FP8 8 small, coarse H100-era training + inference
INT8 8 integer steps Inference quantization
INT4 4 16 distinct levels Aggressive inference quantization

The compression payoff

Going from FP16 → INT4 = 4× less memory and roughly 2-3× faster inference on the same hardware, because memory bandwidth — not compute — is the LLM bottleneck.

Memory Math

weights_bytes = num_parameters × (bits_per_weight / 8)

For a 7B-parameter model:

Precision Weights size Fits on
FP16 14 GB A100 40GB, RTX 4090 (tight)
INT8 7 GB RTX 3090, M2 Max
INT4 3.5 GB RTX 3060 12GB, M1 Pro, laptop

For a 70B-parameter model:

Precision Weights size Fits on
FP16 140 GB 2× A100 80GB
INT8 70 GB 1× A100 80GB
INT4 35 GB 1× RTX 4090 (24GB) — almost, 2 GPUs needed

The “fits on” column is why quantization exists

A 4-bit 70B model on a single consumer GPU is the difference between “needs a data center” and “runs on my desk.”

The Quality Cost

The sweet spot for 2026 — open-weights serving

INT4 (4-bit) is the open-source serving default. Quality loss is small enough that a 70B-int4 outperforms a 13B-fp16 on most tasks — at similar VRAM.

Caveat: hosted SaaS APIs (OpenAI, Anthropic, Google) don’t expose serving precision to consumers — you can’t choose it, and providers may run their own quantized variants invisibly. This session is about precision you control.

C. What Actually Gets Quantized

It is not just the weights

Three Things in GPU Memory

Item What it is Typical size (7B at FP16)
Weights The model parameters ~14 GB
Activations Intermediate computations per token ~0.5-2 GB
KV cache Cached key/value tensors for past tokens Grows with context length

KV cache grows linearly with context

At 32K context, a 7B model’s KV cache is ~16 GB — bigger than the weights themselves. Quantizing the KV cache (e.g., to INT8) is essential for long-context inference.

Architecture caveat — GQA shrinks this 4-8×

The 16 GB figure is for multi-head attention (Llama 2 7B, older models). Modern 7B/8B models — Llama 3.1, Mistral, Qwen 2.5 — use grouped-query attention (GQA), which shares K/V across heads and cuts the KV cache by 4-8×. For Llama 3.1 8B at 32K, the KV cache is closer to ~2-4 GB, not 16 GB. Still grows with context — just not as ruinously.

What the Methods Quantize

Method Weights Activations KV cache
Weight-only quant (most common) ✅ ❌ (kept FP16) ❌
Weight + activation quant ✅ ✅ (INT8) optional
KV-cache quant (separate concern) ❌ ❌ ✅

Weight-only is the default because activations have a wider dynamic range and quantizing them aggressively hurts quality. KV-cache quantization is the next frontier as context windows grow.

D. Methods Tour

The four names you will see on Hugging Face

The Four Big Names

Method When to use Trade-off
GGUF (llama.cpp) Local-first: CPU, Apple Silicon, and GPU (CUDA / Metal / Vulkan) Single portable file format; drives Ollama, LM Studio, llama.cpp
AWQ High-throughput GPU serving (vLLM / TGI) Calibration-based weight quant; very strong INT4 quality
GPTQ GPU inference on older hardware Layer-by-layer error correction; the original “good” INT4
BitsAndBytes Loading any HF model in 4/8-bit on the fly Easiest to use; not the fastest at inference

Choose by deployment target

  • Laptop / phone / Mac, or single-user GPU box → GGUF (via Ollama or llama.cpp; runs CPU or GPU)
  • Multi-tenant cloud GPU serving → AWQ (via vLLM or TGI) — better batch throughput
  • Quick experiment in a Jupyter notebook → BitsAndBytes
  • Older GPU, need INT4 → GPTQ

BitsAndBytes — Easiest On-Ramp

from transformers import AutoModelForCausalLM, BitsAndBytesConfig

quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",         # "NormalFloat4" — quality-tuned 4-bit
    bnb_4bit_compute_dtype="float16",  # compute in FP16, store in 4-bit
    bnb_4bit_use_double_quant=True,    # double-quantize the quant constants
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B-Instruct",
    quantization_config=quant_config,
)
# 8B model now occupies ~5 GB instead of 16 GB.

One line of config, one library, runs on a 12 GB consumer card.

Why NF4 beats plain INT4

Trained LLM weights are empirically near-normal (mean ~0, bell-shaped distribution). Plain INT4 places its 16 quantization levels at evenly-spaced intervals — wasting codes on the rare tails. NF4 (“NormalFloat-4”) places its 16 levels at the quantiles of a normal distribution, so dense regions of the weight distribution get more resolution. Result: noticeably better quality at the same 4-bit footprint.

GGUF — The Local Default

GGUF is a file format, not a runtime — but it’s what Ollama, LM Studio, llama.cpp, and most edge inference engines speak.

# Pull a pre-quantized model in one command:
ollama pull llama3.1:8b-instruct-q4_K_M
#                          └─ Q4 = 4-bit, K_M = K-quant medium variant

Quant suffix decoder

Q2_K, Q3_K_S, Q4_K_M, Q5_K_M, Q6_K, Q8_0 — the number is bits, K = improved k-quant family, _S/_M/_L = small/medium/large (more storage = better quality). Q4_K_M is the community default for the speed/quality balance.

E. QLoRA Revisited

Putting it all together with last session’s fine-tuning

QLoRA = Quantized Base + LoRA Adapter

From Fine-Tuning in Practice

LoRA freezes the base model and trains tiny adapter matrices. QLoRA adds: store the frozen base in 4-bit during training.

from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model

# 1. Load base model in 4-bit (quantization session content)
quant_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4")
base = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct",
                                            quantization_config=quant_config)

# 2. Wrap with LoRA adapters (Session 4 content)
lora = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"])
model = get_peft_model(base, lora)

# 3. Train as normal — only adapters update, base stays frozen in 4-bit
# trainer.train()

Result: full SFT of an 8B model on a single 16 GB GPU. This is the workflow most open-source fine-tuning tutorials show.

Why This Matters for Deployment

After QLoRA training, you have: a 4-bit base model + a small FP16 adapter file (~50 MB). Two ways to deploy:

Option A — Keep adapter separate (PEFT default). Load 4-bit base + adapter at inference time. Adapter math runs in FP16 over a 4-bit base. Small runtime overhead but you can hot-swap adapters per request.

Option B — Merge for inference. You cannot losslessly merge an FP16 adapter into 4-bit weights. The real workflow is:

4-bit base  →  de-quantize to FP16  →  merge adapter
            →  re-quantize (GGUF / AWQ / GPTQ)  →  serve

The output is a single quantized model with no adapter file — fastest at inference, but no hot-swap.

Which to pick

Hot-swap multiple adapters? Option A. Single specialized model in production? Option B. Ollama / vLLM / TGI all read the Option-B merged-then-requantized output.

F. Wrap-up

Key Takeaways

  1. “Quantization” means two different things. This session is about model weights (LLM compression for inference). Vector quantization in RAG is a separate topic in Production Optimization.
  2. Bits per weight → memory × 4-8 compression. The bottleneck of LLM inference is memory bandwidth, so quantization is also a speed-up — not just a shrink.
  3. INT4 is the open-weights serving sweet spot for 2026. Quality loss is small (~3-5%); the deployment unlock is huge. (Hosted SaaS precision is opaque — this point is about models you serve.)
  4. Pick the method by target hardware. GGUF for CPU/Mac/edge, AWQ for GPU serving, BitsAndBytes for quick experiments, GPTQ for older GPUs.
  5. Activations and KV cache are separate quantization concerns — important as context windows grow.
  6. QLoRA = quantization + LoRA from Fine-Tuning in Practice. Lets you fine-tune 8B+ models on a single consumer GPU. The most common open-source workflow.
