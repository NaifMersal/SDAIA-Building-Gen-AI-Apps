A. Why Self-Host?

The four legitimate reasons to leave the hosted API

The Four Legitimate Reasons

  1. Data sovereignty / privacy. Regulated data (healthcare, finance, government) can’t leave your VPC. Self-host isn’t optional — it’s a compliance requirement.

  2. Cost predictability at scale. Hosted APIs are linear: 10× the traffic = 10× the bill. Self-hosted is step-function: same GPU serves 1 or 1,000 requests up to capacity. Crosses over around $5K-$10K/month in hosted spend.

  3. Latency floor. Network round-trip to a hosted API adds ~50-200ms. For voice agents, real-time copilots, or edge devices, self-hosting eliminates that hop.

  4. Model lock / version stability. Hosted models deprecate. A self-hosted Llama 3.1 will keep behaving identically in five years; a hosted gpt-4-0613 gets rotated out from under you.

The Honest Trade-Off

Hosted API Self-Hosted
Time to first call Minutes Hours to days
Ops burden Zero Significant (GPU monitoring, OOMs, updates)
Cost at low volume Cheap Expensive (idle GPUs cost the same as busy ones)
Cost at high volume Expensive Cheap
Quality Frontier models Open-weight ceiling (Llama, Qwen, Mistral)
Compliance Provider’s problem Your problem
Talent needed Application engineers Application + infra + GPU engineers

Default to hosted for prototypes

Self-hosting is an optimization you earn into. Burning the first month of a project on GPU procurement is usually wrong.

B. Inference Servers

Four engines, four niches

The Engine Landscape

Engine Niche Strength Weakness
Ollama Developer laptops, internal demos One-command install, great DX Single-user; not for production serving
llama.cpp CPU / Apple Silicon / edge Runs anywhere; tiny memory footprint Slower than GPU engines at scale
vLLM High-throughput GPU serving PagedAttention → 2-10× higher throughput than alternatives GPU only; harder to operate
TGI (HuggingFace) Polished HF ecosystem integration OpenAI-compatible API; good docs Slightly behind vLLM on raw throughput

Choose by deployment target

  • Internal tools, personal use → Ollama
  • Production GPU server → vLLM (or TGI)
  • No GPU available → llama.cpp / GGUF
  • Mobile / IoT → llama.cpp + small model

Ollama — Fastest Onramp

# Install (Mac/Linux/Windows installer)
ollama pull llama3.1:8b-instruct-q4_K_M
ollama serve

Then call it from any OpenAI SDK:

from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",  # Ollama ignores the key
)

resp = client.chat.completions.create(
    model="llama3.1:8b-instruct-q4_K_M",
    messages=[{"role": "user", "content": "Hello"}],
)

Same OpenAI() interface as API & Provider Landscape. One-line change in your app code to switch from a hosted API to a local model.

vLLM — Production GPU Serving

# One-off via Docker
docker run --gpus all -p 8000:8000 \
    vllm/vllm-openai:latest \
    --model meta-llama/Llama-3.1-8B-Instruct \
    --quantization awq \
    --max-model-len 8192

Exposes an OpenAI-compatible endpoint at http://localhost:8000/v1.

What you get over plain transformers

  • PagedAttention — KV cache management like an OS page table; ~2-10× throughput.
  • Continuous batching — new requests join an in-flight batch immediately.
  • Built-in OpenAI API server — same interface as hosted providers; integrates with LiteLLM (API & Provider Landscape).

llama.cpp — Edge & CPU

# Run a GGUF model directly (no GPU needed)
./llama-server -m models/llama-3.1-8b-q4_K_M.gguf \
               --port 8080 \
               --ctx-size 4096
  • What runs: anything in GGUF format (see Model Weight Quantization).
  • Where it shines: Apple Silicon (M-series), x86 laptops, ARM SBCs, even phones.
  • Cost story: uses RAM, not VRAM. A 16 GB MacBook runs an 8B-Q4 model comfortably.

Ollama is llama.cpp underneath

Ollama bundles llama.cpp + a model manager + a server + a CLI. If you need finer control (custom kernels, weird hardware, embedded use), drop down to llama.cpp directly.

C. Hardware Sizing

Using the memory math from Model Weight Quantization

The Sizing Formula

From Model Weight Quantization

weights_bytes = num_parameters × (bits_per_weight / 8)

A 7B model in INT4 = 3.5 GB on disk and in VRAM.

But weights are not the whole story:

required_vram ≈ weights_size
              + activation_buffer (small)
              + kv_cache(context_length, batch_size)
              + overhead (~10-15%)

KV cache per token — exact formula, FP16:

bytes_per_token = 2 × n_layers × n_kv_heads × head_dim × 2

Model layers kv_heads head_dim KB / token
Llama-2-7B (no GQA) 32 32 128 ~524 KB
Llama-3.1-8B (GQA-8) 32 8 128 ~131 KB
Llama-2-13B (no GQA) 40 40 128 ~820 KB
Llama-3.1-70B (GQA-8) 80 8 128 ~328 KB

Grouped-Query Attention changes the math

GQA shrinks the KV cache by num_attention_heads / num_kv_heads. Llama-3.1-8B uses 8 KV heads instead of 32 → 4× smaller KV cache than a vanilla MHA design at the same parameter count. This is why modern open-weight models can serve long contexts on consumer GPUs at all — architecture matters more than parameter count for serving cost.

At 32K context per request: Llama-2-7B needs ~17 GB just for KV cache; Llama-3.1-8B needs ~4 GB. Always check config.json for num_key_value_heads before sizing.

Picking a GPU

Model + precision VRAM needed Cheapest reasonable GPU
7-8B INT4 ~5-7 GB RTX 3060 12GB (~$300 used)
7-8B FP16 ~16-20 GB RTX 4090 24GB / A10G 24GB
13B INT4 ~9-11 GB RTX 3060 12GB (tight) / 4070
30-34B INT4 ~20-22 GB RTX 4090 / A10G
70B INT4 ~40-45 GB A100 80GB / 2× RTX 4090
70B FP16 ~150 GB 2× A100 80GB / 1× H100

Headroom matters

Sizing to exactly the weight size is the most common production bug. Leave 30-50% headroom for KV cache, multiple concurrent requests, and CUDA fragmentation.

D. Deployment Patterns

Three topologies for three deployment scales

Pattern 1 — Single-Node

  • One Docker container holds the model.
  • nginx handles TLS, auth, rate limiting.
  • Scales vertically (bigger GPU) or by adding replicas behind a load balancer.
  • Right for: ≤ 100 concurrent users, internal apps, single-model serving.

Pattern 2 — Multi-GPU / Cluster

  • Kubernetes (or Ray Serve) orchestrates replicas.
  • Sharing a model across GPUs uses tensor parallelism (--tensor-parallel-size 2 in vLLM).
  • Right for: thousands of concurrent users, multi-tenant SaaS, or single models too big for one GPU.

Pattern 3 — Edge / Local

  • Model ships with the application (or downloads on first run).
  • No network round-trip; works offline.
  • Quantization is critical — INT4 GGUF is the default.
  • Right for: desktop tools, on-device assistants, regulated environments with no outbound traffic.

E. Operations

The day-2 concerns that turn a demo into a service

What You Now Own

When you self-host, the hosted-API team’s job becomes your job:

Concern Hosted Self-hosted
TLS termination provider you (nginx / Caddy / Traefik)
API keys / auth provider you (gateway + token validation)
Rate limiting provider you (nginx / envoy / Kong)
Observability provider’s dashboard you (Prometheus + Grafana)
GPU OOM handling invisible you (restarts, alerting)
Model updates automatic you (download, restart, validate)
Cost monitoring invoice line you (GPU utilization + electricity)

A Minimum-Viable Production Stack

LiteLLM doubles as a self-hosted gateway

The same LiteLLM you used as a client library in API & Provider Landscape also runs as a proxy server — adding auth, routing, and cost tracking in front of your vLLM cluster. One tool, both ends.

Updates Without Downtime

Models are large; rolling updates need a strategy

A 70B model download can take 10+ minutes. You can’t restart a serving pod during a request.

Two common patterns:

  1. Blue/green — stand up new pods with the new model, switch traffic via the load balancer, drain old pods. Doubles GPU spend briefly.
  2. Adapter hot-swap — keep the base model running, swap LoRA adapters in-process. Near-zero downtime, but only works for fine-tunes (see Fine-Tuning in Practice) — not full model upgrades.

F. Wrap-up

Key Takeaways

  1. Self-host for four reasons: privacy, cost-at-scale, latency, version stability. Anything else is usually premature optimization.
  2. Pick your engine by scale and target hardware. Ollama for dev, vLLM for production GPU serving, llama.cpp for edge / CPU.
  3. Quantization (covered in Model Weight Quantization) is what makes this practical. INT4 GGUF and AWQ are the formats that turn “needs a data center” into “runs on one consumer GPU.”
  4. Size for weights + KV cache + headroom, not weights alone. Long context = surprisingly large KV cache.
  5. You now own ops. TLS, auth, rate limiting, observability, model updates — all your problem.
  6. OpenAI-compatible API is the universal contract. Same SDK calls, swap the base_url. Migration cost between hosted and self-hosted = one config line.
