Simple vs Multi-Stage: Size Comparison

Single-stage build

FROM python:3.11
RUN apt-get install -y gcc g++ curl
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY ./src ./src
# Final image: ~2.3 GB
# Includes: gcc, g++, build cache

❌ Ships build tools to production

Multi-stage build

FROM python:3.11-slim AS builder
RUN apt-get install -y gcc g++
RUN pip install -r requirements.txt

FROM python:3.11-slim AS runtime
COPY --from=builder /opt/venv /opt/venv
COPY ./src ./src
# Final image: ~450 MB
# No build tools!

✅ Lean, secure, fast to pull

C. Writing the AI Dockerfile

Two-stage build with security best practices

The .dockerignore File

Critical: Exclude Before You Build

Without .dockerignore, every COPY . . sends your entire repo context to Docker — including .env files with secrets, __pycache__, virtual envs (GB of data), and git history.

# Python artifacts
__pycache__/
*.py[cod]
*.egg-info/
.venv/
venv/

# Secrets — keep out of the build context (see Section E)
.env
*.pem
secrets/

# Dev tools
.git/
.pytest_cache/
tests/
notebooks/
*.ipynb

# Large model files (mount at runtime instead)
models/*.bin
models/*.safetensors

Multi-Stage Build — How it Works

The two subgraphs become two FROM stages; the cross-stage COPY lifts only the built venv into runtime, eliminating gcc/g++ from the final image (the ~450 MB win from Section B).

Security: Non-Root User

Why it matters:

If your app has a remote code execution vulnerability, an attacker running as root can:

  • Read all files on the container filesystem
  • Escape the container (certain configs)
  • Install backdoors

Running as appuser limits blast radius significantly.

# Create user before switching
RUN useradd \
    --create-home \
    --shell /bin/bash \
    appuser

# Switch to non-root
USER appuser
WORKDIR /home/appuser/app

# Chown copied files
COPY --chown=appuser:appuser \
    ./src ./src

D. Orchestrating with Docker Compose

Multi-service topology for local production simulation

Service Topology

docker-compose.yml — Service Contract

Service Image / Build Key Config Purpose
api build: . env_file: .env, depends_on: qdrant (service_healthy) FastAPI app
qdrant qdrant/qdrant:v1.9.0 volumes: qdrant_data:/qdrant/storage Vector store
prometheus prom/prometheus:v2.51.0 volumes: ./monitoring/prometheus.yml:ro Metrics scraper

Three things to get right:

  1. depends_on condition: service_healthy — not just depends_on: qdrant
  2. Named volume qdrant_data declared at root volumes: level
  3. env_file: .env — never ENV API_KEY=... in Dockerfile

Environment Variables in Compose

The .env / .env.example split and .gitignore hygiene were covered in API & Provider Landscape — the same rules apply here.

Docker-specific: Compose reads .env automatically via env_file:, so secrets are injected at runtime instead of baked into the image:

services:
  api:
    env_file: .env          # injected at runtime, never in the image

Runtime injection is only half the job — Section E covers why .env must never enter the image in the first place.

E. Secrets & Security Best Practices

Never bake secrets — runtime injection patterns

The Secret Anti-Patterns

Never Do This

# ❌ ANTI-PATTERN 1: Hardcoded in Dockerfile
ENV ANTHROPIC_API_KEY=sk-ant-api03-real-key-here

# ❌ ANTI-PATTERN 2: Baked in during build
COPY .env .env

# ❌ ANTI-PATTERN 3: Passed as build arg (visible in image layers)
ARG API_KEY
ENV ANTHROPIC_API_KEY=$API_KEY

Always Do This

# ✅ Runtime injection via env_file
services:
  api:
    env_file: .env          # only on your machine
# ✅ CI/CD: inject from secrets manager
docker run -e ANTHROPIC_API_KEY=$SECRET api:latest

Guard .env in both .gitignore and .dockerignore — otherwise a COPY . . bakes it into a layer docker history can recover.

Cloud Secrets Management

Environment Solution How
Local dev .env file env_file: in compose
GitHub Actions Repository secrets ${{ secrets.API_KEY }}
AWS Secrets Manager IAM role → fetch at startup
GCP Secret Manager Workload identity
Azure Key Vault Managed identity

Production Pattern

Containers should have zero secrets at build time. Secrets are injected at runtime via IAM roles, Vault, or orchestrator-level secrets. Never via environment variables baked into images.

Image Security Scanning

Scan for CVEs before you push:

# Docker's built-in scanner
docker scout cves myapp:latest

# Or Trivy (open source)
trivy image myapp:latest
