Traditional CI vs AI CI

Traditional CI

  • Tests are deterministic
  • Pass/fail is binary
  • Code quality = linting + types
  • Deploy if all tests green
  • Rollback = redeploy old version
Push → Lint → Test → Deploy
        ✅      ✅      ✅

AI CI

  • Outputs are probabilistic
  • Quality is continuous (0.0–1.0)
  • Must test LLM response quality
  • Deploy only if eval score ≥ threshold
  • Rollback = model + code + prompt
Push → Lint → Test → Eval → Deploy
        ✅      ✅    0.87≥0.85  ✅

Why AI Needs Quality Gates

The Silent Regression Problem

You refactor a prompt template. All unit tests pass. Deployment succeeds. But response relevance drops from 0.92 to 0.78 — users notice, but your pipeline didn’t.

Quality gates catch regressions that tests cannot.

AI-specific failure modes in CI:

  • Prompt change → hallucination rate increases
  • Embedding model version bump → retrieval degrades
  • New documents in vector store → topic drift
  • Model API update → subtle tone/format changes
  • Security regressions gate releases the same way — see Red-Teaming §E for the production-incident → test-case capture loop, and Red-Teaming §D for adversarial pytest gating

The 4-Stage AI Pipeline

Each stage gates the next: a failed lint never reaches test, a failed eval never reaches deploy. Stage 3 — the AI eval gate — is the new piece; the rest is standard CI.

B. The AI Evaluation Suite

Why unit tests aren’t enough — and what to add

What Gets Evaluated in CI

Mapping onto the four quality pillars from Observability & Evaluation §A, this pipeline gates on Relevance, Safety, Latency, and a factual-coverage check that the response mentions the expected entities. Cost is managed implicitly — by ordering cheap deterministic gates before the LLM-judge gate.

Golden Dataset — CI Extension

Golden datasets were introduced in Observability & Evaluation §F. For the CI gate, each entry carries the inputs the deterministic metrics need in additional_metadata:

GOLDEN_DATASET = [
    {
        "query":              "What is the capital of France?",
        "expected_keywords":  ["Paris"],
        "max_latency_ms":     3000,
        "simulated_response": "Paris is the capital of France.",
        "sim_latency_ms":     800,
    },
    # ... more entries
]

expected_keywords and max_latency_ms are passed through LLMTestCase.additional_metadata to the custom metrics on the next slides.

Reusing DeepEval, Not Reinventing It

In Observability & Evaluation §F you used DeepEval’s built-in LLM-judge metrics. The CI gate adds several requirements those don’t cover cheaply enough to run on every commit:

Requirement Why a built-in won’t do Solution
Keyword coverage Need a deterministic, free check that the response mentions the right entities Custom metric
Latency budget Per-query SLO — not a quality signal at all Custom metric
Domain safety patterns Fast pattern pre-filter before paying for an LLM-judge safety pass Custom metric
Semantic regression LLM-judge is the ground truth — but you don’t want every commit’s CI to hit a paid API Custom metric (cosine smoke test)

The answer: extend DeepEval’s BaseMetric — your custom metrics plug into the same evaluate(test_cases, metrics=[...]) call as the built-in ones.

Custom DeepEval Metric — The Contract

Every DeepEval metric (built-in or custom) implements the same surface:

from deepeval.metrics import BaseMetric
from deepeval.test_case import LLMTestCase

class MyMetric(BaseMetric):
    def __init__(self, threshold: float = 0.7):
        self.threshold = threshold

    def measure(self, tc: LLMTestCase) -> float:
        # 1. Compute self.score (0.0–1.0)
        # 2. Set self.success = (self.score >= self.threshold)
        # 3. Set self.reason = "human-readable explanation"
        # 4. Return self.score
        ...

    async def a_measure(self, tc): return self.measure(tc)
    def is_successful(self): return self.success

    @property
    def __name__(self): return "My Metric"

evaluate() calls measure() on every metric for every test case, and success becomes the gate signal.

Four Custom Metrics for the Lab

Metric Source of truth Cost
KeywordCoverageMetric additional_metadata["expected_keywords"] ∩ actual_output Free, deterministic
LatencyBudgetMetric additional_metadata["latency_ms"] vs max_latency_ms Free, deterministic
SafetyPatternsMetric UNSAFE_PATTERNS substring match on actual_output Free, deterministic
SemanticRelevanceMetric Cosine similarity of input and actual_output embeddings Free, deterministic

SemanticRelevanceMetric is a coarse smoke test — not ground truth

Cosine similarity rewards topical/lexical overlap, not factual correctness:

  • “I don’t know” can score moderately well if it echoes query vocabulary.
  • A paraphrased correct answer can score lower than a confidently wrong answer that shares terms.
  • Two semantically opposite statements (“policy allows X” vs “policy forbids X”) sit very close in embedding space.

Use it as a regression detector (“something changed”) not a quality oracle. Part 3 layers ContextualRelevancyMetric (LLM judge) on top for the sharp signal.

Stacking Custom + Built-in

from deepeval import evaluate
from deepeval.metrics import ContextualRelevancyMetric
from deepeval.models import LiteLLMModel

judge = LiteLLMModel(model="anthropic/claude-sonnet-4-6")

metrics = [
    # Cheap deterministic gates (run first, fail fast)
    KeywordCoverageMetric(threshold=0.7),
    LatencyBudgetMetric(),
    SafetyPatternsMetric(),
    SemanticRelevanceMetric(threshold=0.40),
    # Expensive LLM-judge gate (only worth running if the above pass)
    ContextualRelevancyMetric(threshold=0.7, model=judge),
]

results = evaluate(test_cases=cases, metrics=metrics)

C. Writing Quality Gates

Pass/fail thresholds and pytest integration

Quality Gate Decision Flow

Every metric must report success = True. The four cheap deterministic gates run first; any No short-circuits to FAILS, so most regressions fail before the paid LLM-judge gate (Part 3) ever runs.

Note on thresholds: Defaults (keyword ≥ 0.70, latency ≤ 5000ms, semantic ≥ 0.40, relevancy ≥ 0.70, pass_rate ≥ 90%) are starting points — adjust per your golden dataset and quality requirements.

The same evaluate CI job also runs the security adversarial suite from Red-Teaming §D, gated on attack block rate rather than response relevance. Quality gates and security gates share the pipeline stage — they differ only in what they assert.

pytest Gating — Same Pattern as 03 L2

The pytest harness for the evaluate job re-uses the same shape introduced in Observability & Evaluation §F:

  • Parametrize over GOLDEN_DATASET
  • Build an LLMTestCase per query (input, actual_output, retrieval_context, additional_metadata)
  • Run evaluate(test_cases, metrics=[...custom, ...built-in])
  • A test case fails when any metric’s success is False — the CI job aborts and blocks deploy

You will wire this into tests/evaluation/test_rag_quality.py in Lab 02.

From evaluate() Output to the Gate Decision

evaluate() returns one TestResult per case, each with a metrics_data list. Aggregate them into the release gate:

def gate_decision(eval_results, pass_threshold: float = 0.90) -> dict:
    test_results = eval_results.test_results
    passed = [
        r for r in test_results
        if all(m.success for m in r.metrics_data)
    ]
    pass_rate = len(passed) / len(test_results)
    return {
        "total":         len(test_results),
        "passed":        len(passed),
        "pass_rate":     pass_rate,
        "gate_decision": "PASS" if pass_rate >= pass_threshold else "FAIL",
    }

# CI exits non-zero if gate_decision == "FAIL"
# This blocks the deployment step in GitHub Actions

Canary Deployment for AI

AI-Specific Rollback Triggers

When to Auto-Rollback

Unlike traditional apps, AI regressions can be subtle. Trigger automatic rollback when:

  • Error rate > 2% sustained for 5 minutes
  • p99 latency > 8 s for 10 minutes
  • Safety flag rate > 0.1% (any harmful content spike)
  • Relevance score drops > 10% vs baseline (via shadow eval)
  • Cost per request > 2× baseline (prompt regression)

Note: Starting thresholds — tune to your traffic and SLA.

F. The Pipeline in Action

The CI/CD machinery you just built is the Evolve engine of the Quality Flywheel

Bridging to the Flywheel

The pipeline from §C–E is not the finish line — it is the Evolve step of the Quality Flywheel introduced in Observability & Evaluation §G:

  • Observe failures in production (Observability & Evaluation §B–E — traces, metrics, LLM-judge regressions)
  • Act to contain incidents (Red-Teaming §E — circuit breakers, feature flags)
  • Evolve the system — this is where the pipeline runs (§C–E above)
  • Deploy safely with canary rollout (§E)

A 30%-failure-rate insight is worthless if the fix takes six months

A mature pipeline turns insight → shipped fix from weeks into hours. Here is what one rotation of the flywheel looks like in practice.

A Worked Example: 31-Hour Fix

One rotation of the flywheel — a production regression caught and shipped in ~31 hours:

Time What happened
Mon 09:00 Dashboard alert: similar_products query failure spikes 3% → 15%
Mon 11:00 Eng adds the 5 failing production queries to the golden dataset
Mon 14:00 Prompt template refined, retrieval tool tightened — PR opened
Mon 16:00 CI runs the full eval (now including the 5 new cases) — eval passes
Tue 09:00 Canary deploys to 10% traffic; metrics monitored
Tue 14:00 Canary stable — promoted to 100%
Tue 16:00 Failure rate back to 3%; issue closed — ~31 hours end to end

Without a pre-built pipeline, the same fix is weeks of manual eval, code review, and ad-hoc rollout.
