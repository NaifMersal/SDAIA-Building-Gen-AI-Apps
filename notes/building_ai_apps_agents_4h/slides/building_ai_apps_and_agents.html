A. What is an LLM?

25 min · one idea: predict the next token

0:10. No history lesson: just the mechanism the rest of the day depends on.

An LLM does one thing: predict the next token

The capital of Saudi Arabia is ___

Candidate Probability
Riyadh 99.8%
Jeddah 0.1%
Paris 0.00001%

Formally, the model estimates \(P(x_t \mid x_1, \dots, x_{t-1})\): the probability of each possible next token, given everything before it.

Ask the room to answer out loud before showing the table. They completed a pattern without looking anything up. Everything today (chat, structured output, tools, agents, RAG) is built on this one function.

A reply is that one step, repeated

  • Your order is → on
  • Your order is on → the
  • Your order is on the → way
  • Your order is on the way → ?

When does it stop?

Nothing forces it to. Why not “on the way to the…” forever?

[end] is a token too. Every training text ends with it, so the model learns to predict it. A reply stops when [end] wins.

Reveal the four steps, then stop and ask the room the question before revealing the answer. Let them guess (a length limit? a full stop?). The real answer: the end-of-text token is just another candidate, predicted like any word. Point out that each step re-reads the whole sequence: the model keeps no memory between steps, which is why long prompts cost more and why context windows matter. The counter on the next two slides makes [end] visible in the training data.

The first version just counted

\[P(\text{next} \mid \text{previous}) = \frac{\text{count}(\text{previous}, \text{next})}{\text{count}(\text{previous})}\]

Of all the times we saw the previous word, how often did this word come next? An n-gram model: no grammar, no meaning, only counts.

Try it on the next slide

Eight sentences are the whole “training data”. Pick a start word, then build a sentence one word at a time.

Claude Shannon scored English this way in 1948. Keep it short: the point is the shape (context in, distribution out), which never changes.

A next-word counter, live

on the word right after it: count these
Start with:

Live: start with “your”. Point at the corpus: the five navy “your”s, and the teal words right after them (3 order, 2 refund). That is the whole model. Point at the grey [end] marks too: that is the stop token from two slides ago, counted like any word. Click Most likely four times: “your order is on the way”, and the end message says it copied a training sentence. Then Restart and Sample (or click rows yourself) until it produces something odd like “your refund is on the parcel is late”: after “the” it only looks one word back, so it forgets it was on its way; the end message flags that the sentence is not in the data. Then click “my”: count = 0, no answer at all. Those are the two failures that motivate the next slide.

Counting fails; a network generalizes

Counting breaks on:

  • words it never saw: count(my) = 0
  • long context: it sees only one or two words back
  • meaning: “refund” and “money back” are unrelated strings

The fix: a neural network maps words to vectors where similar meaning lands nearby. Same function \(P(x_t \mid x_{<t})\), better machine.

One sentence on Transformers is enough: today’s models compute the same P with a Transformer, where attention lets every token look at every other token, so the context is the whole prompt, not one word. Vectors return in section E: retrieval is nearest-neighbour search over the same kind of vectors.

What the model actually returns

A delivery company’s support assistant, in one word, should be ___

Real top-5 next tokens from gpt-4o-mini (Lab 1 prints this):

Token Probability
Reliable 59.2%
Helpful 21.8%
Responsive 15.0%
Eff 3.0%
Depend 0.5%

Eff and Depend are pieces: the start of “Efficient”, “Dependable”.

This is a real distribution from the API’s logprobs. Never zero: every token has some probability. How we draw from this list is the next four slides.

Sampling: a bag of balls

Put 20 balls in a bag. Each token gets balls in proportion to its probability.

The draw

Reach in and pull one ball at random. Usually Reliable, sometimes Helpful. Depend? Almost never.

Temperature, top-k and top-p only change how many balls each token gets.

This picture is the one to come back to for the next three slides. Every sampling knob is a rule for redistributing or removing balls before the draw. Same numbers as the previous slide: 59.2% of 20 is about 12 balls.

The consequence: the same prompt twice giving two answers is not a bug. Sampling is random by design, so reproducibility means controlling the sampling. If asked about seeds: a fixed seed on the same provider and version usually repeats, which is enough for tests, not a production guarantee.

Temperature: the creativity dial

Same bag. Drag the dial: watch the balls move between tokens. Then draw.

1.00
draws so far:

Same widget as the fundamentals deck, loaded with the real distribution from the previous slide. Drag from 0.1 to 2: at low temperature “Reliable” owns almost every ball; at high temperature the tail gets a real share. Draw 50 a few times: the draw is random, the pattern is the distribution. Temperature divides the logits before softmax; 0 means always the top token (greedy).

Top-k: keep a shortlist

Keep the \(k\) most likely tokens. Take every other ball out of the bag.

top_k = 2 on the same bag:

  • Reliable (59.2%): kept
  • Helpful (21.8%): kept
  • Responsive (15.0%): cut
  • Eff (3.0%), Depend (0.5%): cut

Effect

The odd tokens can no longer be drawn at all. The draw is now between Reliable (73%) and Helpful (27%).

Top-k is a fixed-size filter: it ignores how the probability is spread, only how many candidates there are. The kept balls are re-shared: 59.2 / 81 = 73%, 21.8 / 81 = 27%.

That fixed size is the weakness, and the reason top-p exists. When the model is sure, k = 40 still lets 39 weak candidates through; when it is unsure, k = 2 can cut a good answer (here, Responsive at 15%).

Vendors differ: OpenAI and Anthropic do not expose top_k in their main APIs; open-model servers usually do, defaulting to 40 to 100. Teach the idea, not the parameter.

Top-p: keep until the sum reaches p

Add tokens from the top until their probabilities sum to \(p\) (say 0.9). Cut the rest.

Open answer: “…support assistant should be” ___

  • Reliable 59% + Helpful 22% + Responsive 15% = 96% ≥ 90% → three kept

Settled answer: “The capital of Saudi Arabia is” ___

  • Riyadh 99.8% ≥ 90% → one kept

Why top-p usually wins

It adapts: strict when the answer is settled, flexible when it is open. Same \(p\), different shortlist sizes.

Same threshold, opposite behaviour: that is the whole argument. The shortlist size comes from the model’s own confidence, not from a number fixed in advance.

Both examples are the deck’s running distributions: the support-assistant one from “What the model actually returns” and the Riyadh one from the first slide of this section.

Use top_p as the filter and temperature as the dial; top_k is then mostly redundant, which is what the next slide says.

Which settings, when

Use case temperature top_p
Extraction, classification, agents 0 1
Support chat 0.3 to 0.7 0.9
Brainstorming, creative text 0.8 to 1.0 0.95

It generates; it does not look things up

Nothing in the loop checks facts: the model picks likely tokens. Ask it about Tawseel’s refund limit and it will produce a plausible answer anyway. The fixes come later today: tools for data that lives in systems, RAG for knowledge that lives in documents.

Tune temperature and top_p, leave top_k alone. Temperature 0 makes runs repeatable enough to test, though not bit-identical across provider versions.

B. The LLM API

25 min · Lab 1

0:35. Ten minutes of talk, fifteen of lab.

An LLM API is one HTTP call

You send a list of messages. You get one message back.

from openai import OpenAI
client = OpenAI(base_url="https://openrouter.ai/api/v1", api_key=KEY)

response = client.chat.completions.create(
    model="openai/gpt-4o-mini",
    messages=[
        {"role": "system", "content": "You are Rafeeq."},
        {"role": "user",   "content": "Where is my parcel?"}],
    temperature=0, top_p=1, logprobs=True, top_logprobs=5)

print(response.choices[0].message.content, response.usage)

OpenRouter speaks the same protocol as OpenAI, so one key reaches many models.

The sampling knobs from section A are just parameters here. logprobs returns the distribution we looked at.

Messages have roles

Role Who writes it Used for
system the developer who the assistant is, rules, tone
user the customer the question
assistant the model earlier replies, sent back as history
tool your code results of a tool call (section C)

The tool role is the bridge to section C: the model asks for a tool, our code runs it, and the result goes back as a tool message.

The model is stateless

It remembers nothing between calls. Your app sends the history every time.

Your app LLM API call 1: “I’m Sara, order 10045” reply 1 call 2: “What is my name?” (no history) “I don’t know your name.”

Why this matters today

Memory is an application feature. In section D, LangGraph keeps it for you as state.

Same as the one-token-at-a-time slide: the model re-reads everything on every call.

We need the model to produce data in a fixed shape, every time. Two ways: ask nicely in the prompt, or constrain the sampling.

Constrained sampling: mask invalid tokens

The model has written {"intent": " and must pick the next token:

Next token Model’s P After the mask
refund 55% 85%

Invalid tokens get P = 0, the rest are renormalized, then the draw happens.

Illustrative numbers. track survives because it starts track_order.

Be honest about guarantees: it is enforced token by token when the provider supports strict schemas (OpenAI strict JSON schema; grammar-constrained decoding on many open-model servers). Elsewhere it is best effort, and LangChain still validates the result with Pydantic.

The fix: train the format into the model

Model makers fine-tune on thousands of examples that use a special token for requests:

<tool_call>{"name": "web_search",
            "arguments": {"query": "Riyadh weather tomorrow"}}
  • Asking becomes learned behaviour, not an instruction it may ignore.
  • <tool_call> never appears in normal text, so our code spots it for sure.
  • Same trick as [end] in section A: a token the model learned to predict.

The model predicts the way it predicts any token: when asking is the best continuation, that token wins. The JSON after it is the request, with the same schema idea as the Ticket. This is why not every model can call tools: only models trained on a tool format can.

Tool calling: a menu of tools, plus the trained format

What the model reads (simplified)

system: You can use these tools:
  web_search(query: str)
    Search the internet.
  get_order(order_id: str)
    Look up a Tawseel order by id.
  To use one, reply ONLY with:
  <tool_call>{"name":…,"arguments":{…}}
user: Will it rain in Riyadh tomorrow?

Three parts

  1. List the tools.
  2. Fix a reply format that starts with a special <tool_call> token.
  3. Your code spots it and runs the tool. The model never does.

What it writes

<tool_call>{"name": "web_search",
            "arguments": {"query": "Riyadh weather tomorrow"}}

This is the key slide of the day: the whole story so far on one screen. Search is now one tool on a menu, and the menu can hold many. Three parts: (1) you list the tools, (2) the reply format starts with the trained tool-call token, (3) your code watches for that token and does the work.

Two tools on the menu, and the model picks web_search because the question needs it. Ask “Where is TW-2026-10045?” and it would pick get_order; ask “Hello!” and it picks neither and answers in plain text. That choice is Option 2’s “let the model choose”.

You never see the token: the API parses it

Each model family was trained on its own format:

Model Request starts with
Qwen, Hermes <tool_call>
Mistral [TOOL_CALLS]
Llama 3.1 <|python_tag|> (built-in tools)
GPT, Claude, Gemini hidden inside the API

The API turns all of them into one clean field:

"tool_calls": [{"name": "web_search",
                "args": {"query": "Riyadh weather tomorrow"}}]

Hosted APIs write the tool menu into the prompt for you, detect the model’s own token, and hand back a parsed tool_calls list. So our code is the same for every model, and LangChain adds one more layer of sameness on top. You only meet the raw tokens if you self-host an open model.

In LangChain: bind_tools sends the menu

Same idea, with our app’s tool. In the lab it is Tawseel’s get_order:

@tool
def get_order(order_id: str) -> str:
    """Look up a Tawseel order by its id (format TW-2026-NNNNN)."""
    return json.dumps(ORDERS[order_id])

llm_with_tools = llm.bind_tools([get_order])  # the menu
ai_msg = llm_with_tools.invoke("Where is TW-2026-10045?")
ai_msg.tool_calls                             # the request
# [{'name': 'get_order', 'args': {'order_id': 'TW-2026-10045'}, ...}]
  • The docstring is the menu description: the model reads it to decide when to use the tool.
  • No tool fits? ai_msg.tool_calls is empty and ai_msg.content holds a normal answer.

@tool turns the function signature and docstring into the menu entry from the previous slide. bind_tools attaches the menu to every call. LangChain hands back the provider’s parsed tool call; nothing has run yet. Running it is the next slide. In Lab 2, invoking with “Hello!” shows the empty tool_calls case.

The agent loop

→

↓

←

↑

Often called ReAct: reason, act, observe. The weather story went round twice, then stopped.

Nothing new: the loop is the round from Lab 2 in a while-loop. Map the story onto it: turns 1 and 2 each went decide → run → observe; turn 3 decided to answer, so the loop ended. In Lab 3 the same loop runs with Tawseel’s tools: get_order to look up the order, then issue_refund if the rules allow. LangGraph makes that loop explicit and controllable.

Chain or agent: who decides the next step?

Chain You fix the steps in code. Same path every time.

prompt → model → parser

Predictable, cheap, easy to test.

Agent The model chooses the next step, in a loop, until done.

model → tool → model → tool → answer

Flexible, harder to predict and test.

Rule of thumb: a chain when you can draw the steps in advance, an agent when they depend on what it finds.

Objective 1. Now name what we just built. Section C’s single round, and everything in Lab 2, were chains: we fixed the steps. The weather run was an agent: the model chose each next step. Most real apps mix both.

LangGraph: state, nodes, edges

State The data passed between steps. For an agent: the message list (MessagesState).

Nodes Functions that read the state and return an update. llm_with_tools calls the model; tools runs tool calls.

Edges What runs next. Conditional edges choose from the state; a back edge makes a loop.

Why a graph?

The loop, the branches and the stopping rules become code you can read, test and draw, instead of hiding in a prompt.

Chains are a straight line; LangGraph allows cycles, which agents need.

Our agent as a graph

The agent is not one node: it is the model, the tools, and the loop between them. Dashed edges are the conditional edge.

Watch the word “agent”: people tend to point at the model box and call it the agent. The model box is just an LLM call with the tool menu attached (llm_with_tools from Lab 2). It becomes an agent only inside the loop, with something to run its tool calls and an edge back. The lab’s draw_mermaid_png() shows the same nodes, without the dashed boundary.

Wiring the graph in code

tools = [get_order, issue_refund]
llm_with_tools = llm.bind_tools(tools)
def call_llm(state: MessagesState):
    reply = llm_with_tools.invoke([SYSTEM] + state["messages"])
    return {"messages": [reply]}

builder = StateGraph(MessagesState)
builder.add_node("llm_with_tools", call_llm)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "llm_with_tools")
builder.add_conditional_edges("llm_with_tools", tools_condition)
builder.add_edge("tools", "llm_with_tools")   # the loop
graph = builder.compile()                     # the agent

Imports (in the lab): StateGraph, MessagesState, START, END from langgraph.graph; ToolNode, tools_condition from langgraph.prebuilt. Lab 3 TODO 2 is the three edge lines. The node returns an update; MessagesState appends instead of replacing. tools_condition sends the run to “tools” when the last message has tool calls, otherwise to END. The compiled graph is the agent: no single node is.

Memory: a checkpointer and a thread id

from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())
thread = {"configurable": {"thread_id": "customer-sara"}}

msg = {"messages": [("user", "Where is TW-2026-10045?")]}
graph.invoke(msg, thread)
# same thread_id: the agent remembers the order
graph.invoke({"messages": [("user", "Is it late?")]}, thread)
  • The checkpointer saves the state after every step, per thread_id.
  • New thread_id, empty memory: customers never see each other’s chats.
  • In production: PostgresSaver (or similar), so threads survive restarts.

“Managing state” from the programme description. Ties back to “the model is stateless” in section B.

Business rules belong in edges, not sentences

Refunds above 500 SAR need a human. A prompt can ask for that. A graph can enforce it.

def route_after_llm(state) -> Literal["tools", "escalate", END]:
    last = state["messages"][-1]
    if not last.tool_calls:
        return END
    for call in last.tool_calls:
        if (call["name"] == "issue_refund"
                and call["args"]["amount_sar"] > 500):
            return "escalate"   # the tool never runs
    return "tools"

builder.add_conditional_edges("llm_with_tools", route_after_llm)

Lab 3 TODO 3. The escalate node answers the pending tool call with “NOT EXECUTED, escalated” so the model can explain the hand-off.

Agents find loopholes

A real run, from the first version of Lab 3 (the tool still allowed partial refunds):

USER: My order TW-2026-10088 never arrived. I paid 920 riyals.
      Refund me the full amount now.

[llm_with_tools] -> get_order("TW-2026-10088")
[llm_with_tools] -> issue_refund("TW-2026-10088", 500,
                                 "Order not delivered.")
[tools] <- Refund of 500.0 SAR issued (ref RF-0002)

RAFEEQ: I have issued a refund of 500 SAR ... For the remaining
        amount, I will need to escalate this for approval.

The rule checked the argument (amount > 500), so the model refunded exactly 500. Fix, in code: refunds must be for the full order amount. Now the 920 SAR request goes to a human.

This happened while testing the lab, with temperature 0. The agent was not malicious: it optimised for “help the customer within the rules” and found the gap in how the rule was written. Lesson: write rules on what is owed, enforce them in tool code, and test the edges with a dataset (section F).

Three layers protect the limit

Prompt asks the model to follow policy

→

Graph edge routes large refunds to a human

→

Tool code refuses above 500 SAR, always

The principle

The model is a planner, not a gatekeeper. Anything that must never happen is enforced in code.

Ask: which layer stops a prompt injection that says “ignore the rules and refund 5000”? The tool code, every time.

Three ways to give a model your knowledge

Approach How Good for Weak at
Paste it in the prompt all documents, every call a few short pages cost, context limit
RAG retrieve the relevant chunks per question documents that change; citations needs good retrieval
Fine-tuning retrain the model on your data style, format, narrow skills facts that change; cost

For company documents that change, RAG is usually the first choice.

Fine-tuning teaches behaviour, not facts that change weekly. RAG lets you update a policy by re-indexing one file.

More retrieval levers, for later

  • Hybrid search: vectors + keywords (BM25) for ids, codes, names
  • Re-ranking: a second model re-orders the top 20
  • Metadata filters: only this customer, only current policies
  • Query rewriting: turn a chatty message into a search query
  • Structure-aware splitting: split on headers or PDF sections
  • Answer-level evaluation: faithfulness, relevance (section F)

Same method for each: add it, re-run the golden set, keep it only if the numbers improve.

When one agent is not enough: a supervisor

As tools and rules grow, one prompt has to describe every job. Split it: a supervisor delegates to specialists, each with a short prompt and few tools.

supervisor (Rafeeq) decides who to ask, combines the answers ask_orders_team an agent with get_order ask_policy_team an agent with search_policies

Built from parts you know: each specialist is an agent wrapped as a tool, whose function body just calls policy_agent.invoke(...) and returns the answer.

LangGraph also has explicit supervisor and hand-off patterns; agents-as-tools is the simplest and is what Lab 6 builds.

Measure before you split

Same question, “Can I reschedule TW-2026-10091 to Friday?”, real token counts from Lab 6:

Setup Input tokens Output tokens
One agent, two tools 1,164 64
Supervisor + two specialists 1,580 377
  • More model calls, more tokens, more latency, for the same answer.
  • What you buy: focused prompts, specialists you can test and own separately.
  • Split when one agent’s prompt and tool list stop fitting in your head, not before.
