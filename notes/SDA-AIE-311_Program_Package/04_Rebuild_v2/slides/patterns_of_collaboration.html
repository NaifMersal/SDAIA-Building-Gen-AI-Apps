The Single-Agent Bottleneck

The run_agent loop from the tool-calling module is powerful, but a single agent doing everything has limits:

  1. Context window saturation — research + writing + self-review crams everything into one conversation
  2. Role confusion — “research thoroughly AND write concisely” produces mediocre results at both
  3. Self-review blind spot — an agent rarely catches its own misreads in the same pass
  4. Sequential execution — one agent can only do one thing at a time

What is a Multi-Agent System?

Multiple specialized agents, coordinated by an orchestrator, each with distinct roles and tools:

This module steps up from one agent doing everything to a small team with clear handoffs.

When Multi-Agent Actually Helps

Scenario Single Agent Multi-Agent
Simple research question Perfect Overkill
Deep research + polished report Context overload by step 8 Specialists stay focused
Compare 3+ independent topics Sequential, slow Parallel research agents
Tasks needing quality gates Agent grades its own work Fact-Checker re-reads Writer’s draft against the research
User needs progress by stage One blob at the end Stream results per specialist

The Multi-Agent Reality Check

  • Premature decomposition — creating 5 agents for a task one agent handles fine. Always start single-agent; only split when you hit a real bottleneck.
  • Hardest to debug — failures span agents and handoffs, not a single trace.
  • Highest cost and latency — every specialist call is another round-trip.

Before You Split: Skills vs. a Team

A multi-agent system isn’t the only way to handle many specialized jobs. Often the lighter answer is one general-purpose agent with a library of skills it loads on demand.

Take a logistics operation with 100 process variants (product type, route, SLA, hazmat flag, region). Four ways to serve them:

Approach What breaks
One giant system prompt Context rot + every-turn token cost
RAG over the runbooks A vector DB whose chunking quality has nothing to do with the actual procedures
Multi-agent — one sub-agent per process 100 deployments, 100 eval surfaces, a complex routing layer
One agent + 100 skills Progressive disclosure ≈ 100 × ~50 tokens of always-on metadata; the 101st variant is a new folder, not a new deployment

Strong activation cues (SKU, origin, weight, SLA) make the skill descriptions sharp — so selection stays reliable even with a large library.

Skills Didn’t Kill Multi-Agent

The skills option collapses many systems that were multi-agent by default. But multi-agent is still the right call by design when you have:

  • Genuine parallelism — independent sub-problems running at once
  • Real capability boundaries — different access, security postures, or external systems per agent
  • Adversarial / check-and-balance setups — one agent reviews another (our Fact-Checker gate, Section E)
  • Heterogeneous models — a cheap router, an expensive reasoner, a vision specialist

The reframing

Skills restored the single-agent option for work that was multi-agent by default, not by design. Start with the lightest primitive that holds; reach for a team only when a boundary above is real.

B. Specialist Roles

Same brain, different personalities

The Specialization Pattern

Every specialist runs the same call path — only two things change:

  • A focused system prompt that constrains its role
  • A curated tool set (only the researcher gets search_web; writer and analyst are pure generation)
# Same function for every specialist — only the prompt and tools differ
SPECIALIST_PROMPTS = {"researcher": ..., "analyst": ..., "writer": ...}

async def call_specialist(specialist, task):
    llm = ChatOpenAI(model=MODEL_NAME, temperature=0)
    if specialist == "researcher":
        llm = llm.bind_tools(SEARCH_TOOL_SCHEMA)   # only the researcher gets tools
    resp = await llm.ainvoke([
        SystemMessage(content=SPECIALIST_PROMPTS[specialist]),
        HumanMessage(content=task),
    ])
    ...   # researcher resolves any search_web tool call, then re-invokes

The Specialization Recipe

Each specialist prompt must define:

Component Purpose
Role boundary “ONLY do X — never do Y”
Quality standard What good output looks like
Failure behavior What to do when the primary approach doesn’t work
Output format Raw findings / polished prose / structured verdict
Specialist Tools Output
Researcher search_web (fail-soft web search) Raw findings with citations
Writer None — pure generation Polished document for target audience
Analyst None — reads findings + draft Evaluation of the research, then a fact-check verdict: approved or revision notes

The Analyst wears two hats

In the lab the Analyst can run before the Writer (evaluate findings, flag contradictions) and after it as a fact-checker. The pre-Writer pass is optional — modern models reason while drafting. The load-bearing role is the post-Writer fact-check: re-reading the draft against the original research with fresh context. That’s the gate we build in Section E.

C. Reasoning Patterns, Named

Three names you already saw separately

Three Patterns, One Idea Each

ReAct — reason, then act, then read

Think → call a tool → read the result → think again. One step at a time, model decides each next move.

You built this in the tool module: run_agent is a ReAct loop.

Plan-and-Execute — decide the route first

Write a full, inspectable plan up front, then run it. Re-plan only when reality breaks the plan.

You will see in §D that Pattern 4 (this deck) is Plan-and-Execute at team level.

Reflection — check your own work

Produce → critique against evidence → revise, bounded by a limit.

You will see in §E: Quality Gates is Reflection at team level — the critic is a separate agent.

Why name them?

The same three ideas keep reappearing — inside one agent’s loop, and across a team’s workflow. Naming them lets you pick one deliberately instead of rediscovering it by accident.

Same Concept, Two Altitudes

Each pattern exists at two scales. The mechanism is identical; only who does the thinking changes.

Pattern Per-agent (inside one loop) Team-level (across agents)
ReAct run_agent: think → tool → observe (no team analogue — it’s the atom)
Plan-and-Execute One agent writes a scratchpad plan Orchestrator emits a typed Plan, specialists execute
Reflection “Let me double-check my answer” in the same context Fact-checker agent with fresh context reviews the draft

Altitude matters for quality

A self-reviewing agent grades its own context — it shares the misreads it is looking for. A separate critic reads with fresh eyes — preview of §E: the cheapest fix isn’t a smarter model, it’s a fact-checker. Same pattern, higher altitude, better signal.

Choosing a Pattern: Cost vs Steps

Each pattern buys reliability with model calls. On one fixed task, the newsroom lab runs all three shapes on the same stub model and counts model calls, tool calls, and tokens per run:

Pattern shape Model calls Typical failure it prevents
ReAct loop 1 per step + 1 final acting without information
Plan-and-Execute 1 plan + 1 per step misrouted / forgotten subtasks
+ Reflection gate +1 critic (+1 revise) per gate wrong-but-polished output

Measured numbers for the three runs (same task, same stub model) are produced live in the lab — labs/multi_agent_newsroom.ipynb, stretch section. (measured — you will generate them in class)

Rule of thumb

Reach for the cheapest pattern that meets the failure risk: exploration → ReAct; known decomposition → plan first; anything user-visible → add a gate.

D. Orchestration Patterns

Three ways to coordinate agents

Pattern 1: Pipeline (Relay Race)

Agents execute sequentially, each passing output to the next.

Researcher

→ findings

Writer

→ report

Output

Each agent trusts its input. If the Researcher cites a stale source, the Writer confidently builds an entire narrative around the wrong numbers — headline, supporting prose, conclusion all hang together — and the pipeline ships work that reads polished and internally consistent but is built on a misread at step 1.

  • Pros: Simple, predictable; each step is easy to debug in isolation
  • Cons: Slow (no parallelism); early errors cascade — the Writer normalizes the misread into a coherent (wrong) story
  • Use when: Tasks have clear sequential dependencies and you can place a review gate at the end (Section E)

Pattern 2: Hub-and-Spoke (Supervisor)

A central Orchestrator assigns tasks and collects results.

  • Pros: Parallel execution, orchestrator controls flow
  • Cons: Orchestrator is a single point of failure
  • Use when: Tasks have independent sub-problems

Parallel Dispatch — Recap from Tool Calling

Scenario Parallelize? Why
Research Topic A and Topic B Yes Independent, no shared state
Research then Write No Writing depends on research results
Fact-check claims A, B, C independently Yes Each check is self-contained
Write then Fact-Check No The check depends on the draft

Rule (unchanged): Parallelize calls that share no data dependencies — whether they are tool executions or specialist agents.

Aside: Sharing the Conversation History

Topology answers who calls whom. There’s a separate question: does each agent see every event, or only its own?

Shared, unified history

All agents append to one log.

  • Tight coupling, full visibility
  • Easy handoffs
  • Context costs grow per agent

Separate, private histories

Each agent keeps its own log; only final outputs cross.

  • Strong encapsulation
  • Lower per-agent context cost
  • Need a contract (A2A, agent-as-tool)

Pattern 3: Shared Workspace

Agents read from and write to a shared state.

  • Pros: Flexible, agents can iterate on shared context
  • Cons: Coordination complexity — who reads what and when?
  • Use when: Tasks require iterative refinement

A specialization of Hub-and-Spoke: the supervisor emits a typed Plan (a list of PlanSteps — task, specialist, depends_on) before dispatching. The plan is data you can log, validate, and replan.

  • Pros: Transparent and debuggable — you see the whole plan up front; dependencies are explicit
  • Cons: Planner quality gates everything downstream; a bad plan misroutes the work
  • Use when: Tasks decompose into a known set of specialist steps with clear dependencies

Production Hardening: DAG & Capability Profiles

As these patterns grow up, two refinements recur:

DAG orchestration — Plan-and-Execute, hardened

  • Decoupled state — handoffs don’t accumulate in the prompt
  • File / message bus — pass schema references, not raw text
  • Protected attention — payloads stay out of the model’s context window

Capability Profiles — swappable “personas”

A version-controlled bundle of active skills + tools + guardrails + model/params. The orchestrator tears down one profile (flushing stale state) before loading the next.

Architecture Mechanism Best for
Linear pipeline Sequential text passing Single-domain, low-complexity
DAG orchestration Graph + file-bus state via schema refs Multi-agent, high-reliability
Capability profiles Swappable tool / skill bundles Role-based, domain-specific agents

E. Quality Gates

Where the Analyst earns its keep

Why Quality Gates? Recall the Cascade

The Pipeline failure mode

  1. Researcher misreads a source
  2. Writer builds a polished narrative around wrong numbers
  3. Each step is locally correct
  4. Pipeline ships a wrong answer

The cheapest fix isn’t a smarter model — it’s a fact-checker.

A second specialist re-reads the draft against the original findings and catches the misread before it ships.

The Review Loop: Enter the Fact-Checker

After the Writer produces a draft, the Analyst (acting as fact-checker) re-reads it against the original research findings — with fresh context, no investment in the prose:

A thorough fact-check could watch for all of these:

  1. Every claim is supported by the research findings (citation traceability)
  2. No fabricated specifics — numbers, names, dates, quotes the research didn’t contain
  3. Confidence preserved — uncertain findings aren’t upgraded to confident statements
  4. No missing critical findings that the research surfaced but the draft dropped

Implementing the Quality Gate

async def _quality_gate(draft, findings, max_revisions=2):
    for revision in range(max_revisions):
        verdict = await analyst_review(draft, findings)   # -> ReviewVerdict
        if verdict.approved:
            return draft                                  # Done
        draft = await writer_revise(draft, verdict.feedback, findings)
    return draft                                          # Ship after max revisions

Always Set max_revisions

Without a limit, the Analyst and Writer can enter an infinite review loop.

The Complete Workflow

Orchestrator Researcher(s) Writer Analyst (Fact-Checker) Phase 1: Research (parallel) Raw findings Phase 2: Write report (with findings) Draft Phase 3: Fact-check draft against findings “Revision needed” Revise with notes Revised draft Fact-check again “APPROVED”

F. Wrap-up

Now that you’ve seen the building blocks — specialists, patterns, gates — here’s the strategic claim.

Mitigations Live in the Harness

So how do you stop early errors from poisoning everything downstream? Not by demanding each agent be 99% reliable — you fix it in the scaffolding around the agents:

Pressure point Harness-level mitigation
Bad early decisions Cheap upfront planning review (catch the misread before it propagates)
Hand-off corruption Structured contracts (typed schemas, not free-text)
Silent quality drops Quality gates after agents (Section E)
Cascade visibility One trace ID across all specialists (Observability & Evaluation)

The agents are commodity. The harness is the product.

Two teams building on the same model will get dramatically different end-to-end results based on the orchestration layer they ship around it.

Key Takeaways

  1. Multi-agent is not always better — start with single agent, split at bottlenecks
  2. Specialization = prompt + tools — same call_specialist path, different role
  3. Four patterns: Pipeline, Hub-and-Spoke, Shared Workspace, and Plan-and-Execute
  4. Parallelism of agents
  5. The harness is the product — mitigations live in the scaffolding, not the model
  6. Quality gates stop cascades — one narrow grounded judge, stack judges not prompts, always cap max_revisions
