B. Context Files — Implicit Project Priming

.hermes.md, AGENTS.md, CLAUDE.md, .cursorrules

What Hermes Auto-Discovers

When a session starts, Hermes scans the working directory for one project instruction file. Priority order:

  1. .hermes.md
  2. AGENTS.md
  3. CLAUDE.md
  4. .cursorrules

. . .

First match wins — one file per session.

. . .

NoteWhy Three Fallback Names?

Hermes reads files written for other agents. The teaching point: convention beats configuration — a shipping agent earns trust by respecting formats users already maintain.

Source: context-files.md — priority order (first match wins)

Progressive Discovery

The directory scan does not stop at session start.

. . .

“As the agent navigates into subdirectories during the session (via read_file, terminal, search_files, etc.), it progressively discovers context files in those directories and injects them into the conversation at the moment they become relevant.”

— context-files.md

. . .

Each subdirectory is checked once per session, then cached.

Context File Size Budget

The discovered project instruction file (e.g., .hermes.md, AGENTS.md, CLAUDE.md) is subject to the following size budget:

Limit Behavior
≤ 20K characters Loaded verbatim
> 20K characters 70% head, 20% tail retained; middle dropped

. . .

TipCompare to Sessions & Memory

This is static compaction — not the LLM-driven summarizer from Lab 01. The instruction file is treated as a fixed asset; truncate, do not summarize.

Source: context-files.md — 20,000-char head/tail truncation

SOUL.md — The Identity File

Separate from project context, Hermes loads ~/.hermes/SOUL.md — a global personality file.

. . .

File Scope Lifetime Primary Role
.hermes.md (and fallbacks) Per project Per session What to do (rules, tools, coding styles)
SOUL.md Global to user Across all sessions Who the agent is (persona, tone, identity)

. . .

NoteCoexistence, Not Replacement

They do not replace each other; they coexist and load together. - .hermes.md captures the codebase’s project instructions. - SOUL.md defines the agent’s core character/persona.

Mixing them is a common foot-gun (e.g., hardcoding project-specific build commands in SOUL.md).

Source: context-files.md — global SOUL.md loaded from HERMES_HOME

C. Context References — Explicit Injection

A grammar for “pull this in now”

The @ Syntax

Hermes exposes a small grammar for inline context injection:

@file:src/main.py
@file:src/main.py:10-25
@folder:src/api
@diff
@staged
@git:5
@url:https://example.com

. . .

Expanded content arrives under an --- Attached Context --- block before the user message hits the model.

Source: context-references.md — @-reference grammar

Budget Caps on Context References

The total expanded size of all @ references in a single message is bounded relative to the target model’s context length:

Threshold What happens
> 25% — soft limit Content still injected, but a warning is appended (the size may hurt model attention / break prefix-caching)
> 50% — hard limit Expansion refused; the message is sent as-is without the attachment, preventing context overflow

. . .

ImportantThe Design Lever

A grammar for context injection — and a budget the grammar can’t blow past. Compare to ad-hoc copy-paste workflows, where there is no budget at all.

Source: context-references.md — 25% soft / 50% hard limits

What Hermes Refuses

Folders cap at 200 files. Git history caps at 10 commits. Binary files are rejected outright. (caps table)

. . .

Fully blocked directories — any file inside (verbatim from docs):

~/.ssh/
~/.aws/
~/.gnupg/
~/.kube/
$HERMES_HOME/skills/.hub/

Plus the $HERMES_HOME/.env file and specific SSH key paths (id_rsa, id_ed25519, …).

. . .

Invalid references degrade gracefully: Hermes emits an inline warning and continues the turn rather than aborting it.

Source: context-references.md — invalid references produce inline warnings, not failures

D. Tools — Capability Toggles with Persistent Execution

Toolsets and the long-lived container — the substrate the agent acts through

Toolsets — a Sampling

web   search   terminal   file   browser
vision   memory   cronjob   delegation

A representative slice — the documented common set is larger (skills, image_gen, tts, session_search, clarify, homeassistant, messaging, …).

. . .

Toggled per session:

hermes chat --toolsets "web,terminal"

. . .

NoteWhy Toggle, Not Filter?

The capability list is part of the system prompt. Fewer toolsets = shorter prompt = cheaper tokens and fewer ways for the model to go off-task.

Source: tools.md — toolsets + --toolsets toggle

Terminal Backends

Hermes does not assume the terminal is your laptop. Six documented backends:

docker | local | ssh | singularity | modal | daytona

. . .

Configured in ~/.hermes/config.yaml:

terminal:
  backend: docker
  docker_image: python:3.11-slim
  container_persistent: true
  timeout: 180

Source: tools.md — six backends + Docker config keys

The Production Trick: Container Persistence

Instead of spawning a fresh container for every single command, Hermes keeps the execution environment alive.

. . .

Dimension Ephemeral / Naive Persistent (Hermes)
Lifecycle Fresh container per command Single long-lived container
State (cd, env) Lost instantly Carries over between tool calls
Dependencies Every pip install re-runs Installed packages are retained
Scope Sandboxed per turn Shared across /new, /reset, & delegate_task

. . .

Why Environment Convergence Matters

A long-lived container allows the agent’s environment to converge (dependencies align, files stay put, configurations stick).

The Engineering Lever: Uptime cost of keeping the container running vs. the install latency of repeating setup.

Source: tools.md — container persistence across tool calls

Background Processes and PTY

Two extra mechanics:

  • terminal(background=true) returns immediately; the process tool inspects and kills jobs.
  • pty=true runs interactive CLIs that need a real terminal (e.g. vim, psql, htop).

. . .

Both are needed for any agent that runs long shell tasks.

. . .

Context Files, References, and Tools are all set up at session start. Next: the two surfaces the agent carries across turns — Memory and Skills.

Source: tools.md — background processes + PTY mode

E. Memory — The Frozen-Snapshot Model

The most surprising design choice

Two Files, One Snapshot

Hermes’s built-in memory lives in ~/.hermes/memories/:

File Holds Size cap
MEMORY.md Agent notes ~800 tokens (~2,200 chars)
USER.md User profile ~500 tokens (~1,375 chars)

. . .

Both are injected into the system prompt at session start.

Source: memory.md — char limits + session-start injection

The Surprising Part

“The system prompt injection is captured once at session start and never changes mid-session.”

— memory.md

. . .

WarningDoes This Contradict Lab 02?

Lab 02 built an online memory pipeline: read, write, retrieve during a turn. This looks like the opposite trade — freeze at session start, no mid-session updates. Hold that thought: it’s only half the story (resolved in three slides).

Why Freeze? Prefix Caching.

Recall §1.C — Prefix Stability: the model’s KV cache hits only when the prefix is byte-identical to a prior turn.

. . .

If memory changes mid-session, the prefix changes — and every turn pays the full re-encoding cost.

. . .

Freezing memory turns the entire prompt prefix into a stable cache key. Updates land on disk and apply next session.

. . .

“Mid-session writes update disk state but do not mutate the already-built system prompt until a new session or forced rebuild occurs.”

— prompt-assembly.md

. . .

TipThe Design Lever

Latency now vs. freshness now. For the always-on profile, Hermes picks latency — and pays for that freshness elsewhere, by design rather than by accident.

Source: context-compression-and-caching.md — stable-prefix cache design (“cache hits require prefix matching”)

Mid-Session Edits Still Happen

The agent can edit memory during a turn — via the memory_tool:

memory_tool(action="add",     target="memory", content="user prefers Python over Go")
memory_tool(action="replace", target="memory", old_text="prefers Python", content="prefers Rust")
memory_tool(action="remove",  target="memory", old_text="prefers Python")

. . .

replace and remove use substring matching.

. . .

Same freeze rule as above — the edit persists to disk now, but only reaches the model next session.

Source: tools/memory_tool.py — “replace/remove use short unique substring matching”

Beyond MEMORY.md — The State DB

The 800-token MEMORY.md is intentionally small. Long-term knowledge lives elsewhere:

  • SQLite at ~/.hermes/state.db
  • FTS5 full-text search across all past conversations
  • Retrieved on demand by the agent

. . .

NoteWhy FTS5 and Not Vectors?

Built-in SQLite FTS5 keeps the core agent self-contained: zero extra dependencies, keyword-fast queries, and zero embedding costs. If you need vectors, semantic search, or knowledge graphs, you layer them on via external memory providers (like Honcho or Mem0).

Source: memory.md — SQLite state.db + FTS5 full-text search

Frozen and Fresh — The Resolution

That “contradiction” with Lab 02 dissolves once you see there are two memory layers:

Layer Holds When it loads Why
Frozen profile MEMORY.md + USER.md Once, at session start (system prompt) Cache-stable prefix
On-demand recall state.db (FTS5) + providers Per turn, into the current message Fresh, relevant facts

. . .

Not latency vs. freshness — latency and freshness, split across two layers. The small always-on part stays in the cache-stable prefix; the big searchable part rides in the (uncached) tail.

How Recall Gets In — Without Leaking Out

Per turn, recalled memory is wrapped and slipped into the current message to defend against dialogue-injection:

<memory-context>
[System note: the following is recalled memory context, NOT new user input.]
…retrieved facts…
</memory-context>

. . .

TipThe Unsung Hero: StreamingContextScrubber

The model must see this block; the user must not. A scrubber statefully strips these tags from the streaming output to:

  • Prevent Echoing: Stop the model from parroting back XML tags or repeating prompt patterns.
  • Intercept Updates: Intercept and parse self-written memory updates before they are displayed.

It statefully buffers and strips these tags across streaming chunk boundaries to prevent leaks.

Source: agent/memory_manager.py — build_memory_context_block, StreamingContextScrubber

External Providers Are Additive

The developer docs list eight plugin providers: Honcho, Mem0, Hindsight, OpenViking, Holographic, RetainDB, ByteRover, Supermemory.

. . .

“External providers run alongside built-in memory (never replacing it) and add capabilities like knowledge graphs, semantic search, automatic fact extraction, and cross-session user modeling.”

— memory.md

. . .

ImportantSubtle Design Choice

Providers are additive, not replacements. The built-in memory is always present. The complexity tax goes up with each provider added.

CLI Surface

hermes memory setup     # configure external providers
hermes memory status    # show active providers
hermes sessions list    # browse past sessions

. . .

Every memory entry passes through security scanning: prompt-injection patterns, credential exfiltration, invisible Unicode.

Source: memory.md — security scanning + session-search CLI

Agent-Authored Skills — Closing the Loop

Skills ended on a frontier question: what if the agent writes its own skills?

. . .

Hermes ships this:

  • The agent drafts a new SKILL.md capturing what worked, via the skill_manage tool
  • Skills are versioned and pruned over time

. . .

WarningRecall §1.F — Procedural Memory Failure Mode

LLM-authored skills are still LLM output. The §1.F lesson stands: version, gate, and prune — raw “self-improving” loops drift, they don’t learn.

. . .

When and how this fires — inline mid-turn vs. a background review after the reply — is the learning loop in §G.

Source: tools/skill_manager_tool.py — agent-authored skills via skill_manage

Token Efficiency: Write vs. Patch

Generating a complete SKILL.md file every time a playbook is updated is a fast track to token bankruptcy.

. . .

Just like the memory_tool uses substring matching to avoid rewriting MEMORY.md, Hermes handles skill updates through targeted action parameters inside the skill_manage tool:

  • create: Instantiates a brand new playbook when a novel workflow is recognized.
  • patch (Preferred): Targeted find-and-replace (old_string → new_string) to edit minor rules or pitfalls in an existing skill.
  • edit: Executes a complete rewrite when a playbook undergoes a major structural change.

. . .

The Lesson: In production-grade agents, editing state is treated like a database update — choose the narrowest possible write payload (patch / substring match) to keep context cache keys stable and token costs low.

Source: tools/skill_manager_tool.py — skill_manage tool; skills.md — actions table

G. The Learning Loop — Anatomy of One Turn

Two moments read context in, one records the turn, three make the agent better — one inline, two deferred

One Turn, Annotated

The agent-loop docs spell out one turn as a pipeline. Six points on it are where memory, skills, and self-improvement hook in — marked ①–⑥ on the step each attaches to. The source wires them; this is not present in the developer docs.

. . .

  1. Append user message
  2. Build / cache system prompt
  3. Preflight compression if context > 50%
  4. Construct API messages — ① Recall: prefetch_all(query), cached once/turn, reused across tool iterations
  5. Inject ephemeral layers (budget + context-pressure warnings) — ② Skill load: matched SKILL.md body loaded on demand
  6. Call the model (interruptible)
  7. Parse → tool loop or final text — ③ Inline skill-write: agent calls skill_manage mid-loop to save a win (resets _iters_since_skill)
  8. Persist session — ④ messages + token counts → SQLite · ⑤ Nudge: check the per-turn memory counter and the per-iteration skill counter against their intervals (next slide)

. . .

⑥ Async review — memory + skill review forked after the reply is delivered.

Sources: agent-loop.md — one-turn pipeline; >50% preflight compression at #L203; tool_executor.py — skill_manage resets _iters_since_skill; conversation_loop.py — _should_review_memory / _turns_since_memory

③/⑥ — Two Paths to a Skill Write: a Moment or a Clock

A skill gets written one of two ways — the agent recognizes a moment, or a clock runs out.

③ Inline — a moment ⑥ Background — a clock
What triggers it a moment the agent recognizes mid-turn (SKILLS_GUIDANCE):
• 🏋️ worked hard — 5+ tool calls
• 🔧 fixed a tricky error
• 🧩 found a reusable workflow		 a counter reaches its interval (default 10)
When it runs during the turn, as a normal tool call after the reply is delivered, on a forked thread
Who writes the agent itself a throwaway review fork — memory + skills tools only
Why it exists capture the win the instant it happens safety net for what the agent forgot

. . .

NoteBoth end in the same write

The nudge only prompts a write — both paths finish with the same skill_manage call. An inline write resets the counter, so being proactive pushes back the next background review. And the fork sets its own interval to 0, so a review can’t trigger another review — no runaway loop.

Sources: inline — prompt_builder.py (SKILLS_GUIDANCE — the three qualitative triggers) + tool_executor.py (write resets counter); background — conversation_loop.py (nudge → review), agent_init.py (_skill_nudge_interval, default 10) + background_review.py (forked review, _SKILL_REVIEW_PROMPT)

Up Close: The Clock — Same Number, Different Units

We said ⑥ fires when a clock runs out. There are really two clocks — ⑤ checks both at the end of each turn — and they’re not even in the same unit:

Memory nudge Skill nudge
Counter _turns_since_memory _iters_since_skill
Ticks +1 per user turn tool-loop iteration (each API call in the loop)
Interval (default) _memory_nudge_interval (10) _skill_nudge_interval (10)
Checked at the end of each turn after the tool loop finishes
Resets to 0 when the nudge fires (every N turns) a skill is actually written (③) — not at turn boundaries
So the cadence tracks how much conversation passed how much work the agent did

. . .

TipSame Interval (10), Two Different Clocks

Memory ticks on turns; skills tick on effort. A busy, tool-heavy turn races the skill counter toward a nudge while barely moving the memory counter. And the skill counter only clears when the agent writes a skill — so an inline save (③) pushes back the next background nudge (⑥); skip writing and it climbs across turns until ⑥ fires.

The reset asymmetry is the subtle part: the memory counter resets inside its own check (every time it fires), while the skill counter is never reset by the check — only by an actual skill_manage write. That is what lets proactive inline writes defer the background review.

Sources: conversation_loop.py — _turns_since_memory (+1/turn, checked & reset on nudge); skill counter +1/iteration, checked after the loop, persists across turns; tool_executor.py — skill_manage resets _iters_since_skill; agent_init.py — both intervals default 10

Read In, Record, Improve

The loop does three jobs per turn — and the third is what makes it a loop, not a line:

  • Read in (① ②) — answers this turn.
  • Record (④) — closes it.
  • Improve (③ ⑤ ⑥) — stocks the next one.

. . .

Two threads from earlier in the module tie off here:

  • Memory is agent-curated, not auto-extracted — Hermes periodically asks the agent rather than mining every turn (§1.E).
  • The scheduled review runs off the critical path, forked after the reply ships — §1.G’s “never block on memory writes,” shipped.

. . .

TipIn one sentence

Each turn answers the user and leaves the agent slightly better stocked — fresher memory, maybe a new skill — ready for next time.

Source: agent/conversation_loop.py — _should_review_memory, _turns_since_memory, _memory_nudge_interval; async review in agent/background_review.py

Four Questions for Any Agent Runtime

After reading the Hermes developer docs, ask the same four questions of any new agent you encounter:

  1. Where do project instructions enter? (Context Files)
  2. How does the user inject ad-hoc context? (Context References)
  3. Where does long-term knowledge live? (Memory)
  4. How does the agent acquire new procedures? (Skills)

. . .

A fifth, for any system that runs code: what is the execution boundary, and does it persist? (Tools)

From Prompt Engineering to Context Engineering

Recall from API & Provider Landscape: every turn, you re-send the entire messages list. That re-send is the constraint Context Engineering responds to.

Prompt Engineering

  • Crafts a static system prompt
  • Optimizes wording, examples, format
  • Pays off once, used everywhere
  • Necessary, not sufficient

Context Engineering

  • Dynamically assembles the entire payload
  • Selects: history, memories, tools, RAG hits
  • Per-turn decisions on what to include

. . .

Context Engineering is the mise en place of an agent: gather and prepare every ingredient before the model starts cooking.

B. Sessions (Short-Term Memory)

The container for one conversation

What a Session Holds

A session (Short-Term Memory) is one continuous conversation, scoped to one user.

Events (The messages list)

  • user input (text/image/audio)
  • assistant response
  • tool_call — agent decides to use a tool
  • tool_output — the tool’s result

State (working memory / scratchpad)

  • Items in a shopping cart
  • Form fields collected so far
  • Intermediate calculations
  • Anything transient to this conversation

. . .

Events are append-only. State is mutable.

The Familiar Shape

You already know this from API & Provider Landscape:

from litellm import completion

events = [
    {"role": "system",    "content": "You are a helpful assistant."},
    {"role": "user",      "content": "What's the capital of France?"},
    {"role": "assistant", "content": "Paris."},
    {"role": "user",      "content": "And its population?"},
]

response = completion(model="gpt-4o", messages=events)

. . .

This is the events half of a session. The state half (cart contents, form fields, intermediate results) lives alongside it — managed by your code, not the LLM.

Session: A Minimal Implementation

class Session:
    def __init__(self, session_id: str, store):
        self.session_id = session_id
        self.store = store  # any KV-style backend

    # ── Events (append-only) ──────────────────────
    def events(self) -> list[dict]:
        return self.store.get(f"{self.session_id}:events", default=[])

    def append(self, event: dict) -> None:
        events = self.events()
        events.append(event)
        self.store.set(f"{self.session_id}:events", events)

    # ── State (mutable scratchpad) ────────────────
    def get_state(self, key: str, default=None):
        state = self.store.get(f"{self.session_id}:state", default={})
        return state.get(key, default)

    def set_state(self, key: str, value) -> None:
        state = self.store.get(f"{self.session_id}:state", default={})
        state[key] = value
        self.store.set(f"{self.session_id}:state", state)

. . .

ImportantDeterministic Order

Concurrent turns must be serialized — out-of-order events corrupt the conversation. Use transactional writes or per-session locks.

Session Security

A session can contain anything the user said — names, emails, account numbers, free-form personal stories.

Concern Practice
Strict isolation Every read enforces session.owner == request.user (ACLs)
PII redaction Redact before writing to the store, not just before display
Audit log Track who read what, when

. . .

Output Guardrails covers output-time PII redaction. Sessions need PII redaction at write time too — a leaked session log re-exposes everything.

C. Managing Long Context

Why context windows matter, and how to compact them.

Context Windows & Your API Bill

Important128K context ≠ 128K tokens free

Every token in your context window is charged on every request — both the history you send and the reply you receive.

KV-cache intuition: The API caches the mathematical representation of previous tokens so each new word generated is cheap. But the cache lives in GPU memory — and the context window is its size limit.

. . .

Context length Tokens processed (≈ billed cost)
1K tokens 1×
8K tokens 8×
128K tokens 128×

Performance: The Needle in the Haystack

  • Lost in the Middle (Liu et al., 2023): LLMs often ignore facts buried in the middle.
  • Recall Degradation: As context grows, retrieval ability drops.
  • Placement Matters: Put crucial info at the start or end.
  • Needle in the Haystack (NIAH): A classic benchmark testing if a model can retrieve a single target fact (“needle”) hidden inside a massive block of filler text (“haystack”).
  • Lost in the Middle: The heatmap visually represents recall accuracy (green is high, red/yellow is low). Models exhibit a strong primacy/recency bias. They remember facts at the very beginning (start of the prompt) or very end (right before generation) but struggle with details in the middle.
  • Recall Degradation: Recall drops not just due to position, but also due to the total volume of context. The larger the haystack, the lower the recall, even if the model’s token limit is technically larger.
  • Instructor Insight: Emphasize that context window size (e.g., 128k or 1M) is a capacity metric, not an attention/accuracy metric. Dynamic context placement is essential in production.

Sources: Liu et al., 2023 — Lost in the Middle · LangChain Multi-Needle Analysis

Multi-Needle & Reasoning Challenges

Retrieval is the Upper Bound

  1. Fact Volume: Retrieval accuracy drops significantly as the number of “needles” (facts) increases.
  2. Reasoning Penalty: Asking the model to think about multiple retrieved facts is harder than just finding them.
  3. Upper Bound: If the model can’t retrieve it, it can’t reason about it.

  • Multi-Needle Challenge: Real RAG workloads rarely need only one fact. Usually, the model must retrieve multiple independent facts (e.g., “Find all three times the system crashed”). As the number of needles increases, retrieval accuracy drops drastically.
  • Reasoning Penalty: The heatmap/chart compares simple retrieval of multiple needles versus asking the model to perform reasoning/logic over those retrieved facts. Reasoning introduces a massive performance penalty.
  • Retrieval is the Upper Bound: This is the most crucial concept. If the model fails to retrieve even one of the required facts, it has zero chance of reasoning over it. Downstream reasoning fails when upstream retrieval fails.
  • Instructor Insight: Highlight that relying on massive context windows for complex reasoning is fragile. A better pattern is context compaction, parallel sub-queries, or prompting the model to explicitly list retrieved facts before synthesizing.

Source: LangChain Multi-Needle Analysis

Key Levers of Context Optimization

Given the cost and “Lost in the Middle” effects of long context, we need strategies to keep the payload tight.

  • 1. History Compaction: Shrink or summarize the conversation history (e.g., sliding window, recursive summarization).
  • 2. Context Pruning (RAG): Filter retrieved knowledge to only send relevant snippets, not entire documents.
TipReal-Time Cost Tracking

Use litellm’s built-in usage tracking (e.g. completion_cost) to monitor API costs in real-time during development.

History Compaction Strategies

Strategy What it does Trade-off
Sliding window (last N) Keep last N turns, drop the rest Simple, can lose early context
Token truncation Keep most recent messages until token cap Preserves recency, hard cutoff
Recursive summarization LLM-summarize old turns; prepend summary Preserves meaning, adds an LLM call
Hybrid Summary of old + verbatim of recent Best quality, most complex

. . .

NoteIn the wild: Hermes

Hermes’ context_compressor summarizes the middle turns — keeping head and tail verbatim. A direct application of “Lost in the Middle”: compress where the model attends least.

Sliding Window (Simple)

def trim_to_last_n(events: list[dict], n: int = 10) -> list[dict]:
    """Keep system message + last n turns."""
    system = [e for e in events if e["role"] == "system"]
    rest   = [e for e in events if e["role"] != "system"]
    return system + rest[-n:]


# Use during context preparation, not when storing
context = trim_to_last_n(session.events(), n=10)
response = completion(model="gpt-4o", messages=context)

. . .

ImportantTrim the Payload, Not the Store

Storage is cheap; tokens are expensive. Keep the full session history persisted — only compact what you send to the model.

Recursive Summarization

SUMMARIZE_PROMPT = """Summarize this conversation.
Preserve facts, decisions, and open questions."""

def compact(events: list[dict], keep_recent: int = 6) -> list[dict]:
    if len(events) <= keep_recent:
        return events

    old, recent = events[:-keep_recent], events[-keep_recent:]

    summary = completion(
        model="gpt-4o-mini",  # cheap model is fine for summaries
        messages=[
            {"role": "system", "content": SUMMARIZE_PROMPT},
            {"role": "user",   "content": str(old)},
        ],
    ).choices[0].message.content

    return [{"role": "system", "content": f"Earlier conversation summary:\n{summary}"}] + recent

. . .

Run this asynchronously between turns. The next turn just reads the cached compacted version.

When to Compact

Trigger When it fires Best for
Count-based Token / turn count crosses threshold Bursty, predictable workloads
Time-based User idle for N minutes Long-running advisor agents
Event-based Sub-task / topic completes Task-oriented agents

. . .

TipDefault to Count-Based

Cheapest to implement, “good enough” for most agents. Add sophistication only when you have data showing it’s needed.

Prefix Stability: The Cache’s One Rule

The KV cache matches from the front and stops at the first difference: a hit requires the prefix to be byte-identical to a previous turn.

. . .

So where you place content matters as much as how much you send:

Position Holds On a change
Stable prefix system prompt, durable memory, tool list Cached — reused every turn
Volatile tail latest user turn, fresh retrieval Re-encoded every turn (cheap — it’s small)

. . .

Change one token early — swap a memory, reorder the tool list — and every token after it re-prefills at full cost. The lever: keep volatile content at the end and treat the prefix as frozen.

TipForeshadow: a production consequence

Hermes Agent (§3) pushes this to its conclusion — it freezes injected memory at session start to keep the prefix a stable cache key, accepting some staleness to keep the hit. Same rule, all the way.

Switching Models Mid-Conversation Breaks the Cache

The “Opus for planning, Sonnet for execution” dropdown looks free — but the KV cache is provider-and model-specific, so the first turn after the switch pays the full context cost (Prefix Stability).

Cost surface Same-model turn First turn after switch
KV cache Hit Miss — full prefill
Tool-call shape in history In-distribution Out-of-distribution
First-token latency Low High
Risk of re-invoking another model’s tools None Real

. . .

TipPractical recommendation

Stay with one model for the duration of a conversation unless you have a concrete reason to switch. If you must switch, inject a system note: “You just took over from another model. Some tool calls in this history are not yours — do not re-invoke them.” Cursor, for example, ships this mitigation.

Source: Cursor — Continually Improving Our Agent Harness

D. Memory

Long-term, cross-session

Sessions vs Memory

Session (Short-Term Memory)

  • One conversation
  • Raw events, verbatim
  • Append-only log
  • Lives & dies with the conversation

Memory (Long-Term)

  • Spans all the user’s conversations
  • Distilled, processed insights
  • Curated (created, updated, deleted)
  • Persists across sessions, forever (or until pruned)

. . .

Session = the messy desk during the project. Memory = the filing cabinet you sort into when the project is done.

What Memory Unlocks

  • Personalization — remember the user’s preferences, history, goals
  • Context window relief — distill 50 sessions into 10 facts
  • Self-improvement — record which strategies worked (procedural memory)
  • Cross-user insight — aggregated, anonymized signal across users

Two Types of Memory

Borrowed from cognitive science:

Type Answers Example
Declarative “What?” “User prefers window seats.”
Procedural “How?” “When booking flights, search direct first, fall back to one-stop.”

. . .

Most memory systems today handle declarative memory. Procedural is the frontier — we’ll come back to it in Section F.

Memory Scope

Who does this memory describe?

Scope Example Use
User "User prefers Arabic responses" Personalization (most common)
Application "Project codename ATLAS = Q4 launch" Shared facts for all users

. . .

ImportantStrict Isolation by Default

User-scoped memory must never leak across users. Application-scoped memory must be sanitized of any user PII.

  • User Scope: Persists forever. Crucial for long-term personalization. Requires strict database-level row isolation (ACLs).
  • Application Scope: Shared across all users (e.g. system configurations, global facts). If updated dynamically by users, it is a high-risk vector for PII leaks or memory poisoning.

The LLM decides: what’s worth remembering, and how does it interact with what we already know?

Influential early treatment: MemGPT: Towards LLMs as Operating Systems (Packer et al., 2023) framed LLM memory as OS-style virtual-context paging. The extract → consolidate retrieval triad we score below traces more directly to Generative Agents (Park et al., 2023).

Extraction

Filter the signal from the noise.

from pydantic import BaseModel

class ExtractionResult(BaseModel):
    facts: list[str]

EXTRACT_PROMPT = """Read the conversation. Extract only durable facts about the user that
would be useful in a future session: preferences, goals, constraints, key context.

Ignore: greetings, jokes, transient state, restated facts."""

def extract(events: list[dict]) -> list[dict]:
    response = completion(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": EXTRACT_PROMPT},
            {"role": "user",   "content": str(events)},
        ],
        response_format=ExtractionResult,  # ← Pass the Pydantic schema
    )
    parsed = ExtractionResult.model_validate_json(response.choices[0].message.content)
    return [f.fact for f in parsed.facts]

. . .

“Meaningful” is application-specific. A wellness coach extracts mood; a support agent extracts ticket numbers. Customize the prompt.

Consolidation

Reconcile new extractions with what’s already stored.

CONSOLIDATE_PROMPT = """Existing memories: {existing}
New extracted facts: {new}

For each new fact, decide:
- CREATE if novel
- UPDATE <id> if it refines an existing memory
- DELETE <id> if it contradicts and supersedes one

Return JSON list of operations."""

. . .

Operation Trigger
CREATE Topic is new
UPDATE Same topic, more nuance (“interested in marketing” → “leads marketing for Q4 launch”)
DELETE Direct contradiction or invalidation
ImportantWithout Consolidation

You get a noisy, contradictory log of every fact ever mentioned — worse than no memory at all.

When to Generate Memory

Strategy Cost Freshness
Every turn Highest Most current
Every N turns Medium Lags by N turns
At session end Lowest One batch per session
Memory-as-a-tool Variable Agent decides — most flexible

. . .

Default: at session end, in the background. Use memory-as-a-tool when the agent should decide (“user just said ‘remember this’”).

Memory-as-a-Tool

Expose memory writes as a tool the agent can call.

def remember(fact: str, scope: str = "user") -> dict:
    """Persist a durable fact about the user.
    Use when the user says 'remember', or when they share a stable
    preference, goal, or constraint worth recalling later."""
    memory_store.upsert(user_id=current_user, fact=fact, scope=scope)

Track where each memory came from.

Source Trust
Bootstrapped (CRM, signup form) Highest — solves cold-start

When sources conflict, the highest-trust + most-recent wins. Without provenance, you can’t resolve conflicts at all.

Retrieval

RAG (which you saw earlier) ranks retrieval by relevance (topical similarity) alone. Memory retrieval needs two extra dimensions (Recency, Importance) on top of that — the triad introduced by Generative Agents (Park et al., 2023):

. . .

Dimension What it asks
Relevance Is this memory topically related to the current turn?
Recency How recently was this captured?
Importance How significant was this memory at generation time?

. . .

# Weights are starting points, tune them.
score = 0.6 × relevance + 0.2 × recency + 0.2 × importance
WarningPut the three on the same scale first

You can use Min-max normalization to normalize each component across the candidate set before weighting.

Where Retrieved Memory Goes

Two placement options, with different trade-offs:

System prompt

You are an assistant.
Known about user:
- Prefers Arabic
- Vegetarian
  • High authority
  • Always present
  • Can over-influence (“everything is about food”)

Dialogue injection / tool

Retrieved as a tool result, mid-conversation.

  • Only when relevant
  • Lower over-influence risk
  • Risk of dialogue injection: model may treat it as something the user said

. . .

Hybrid: stable global facts (profile) in system prompt; episodic facts retrieved as needed.

WarningFailure mode

Procedural memory entries are themselves LLM-generated — a bad playbook persists and re-corrupts every future run. Always score, version, and gate writes behind a success-rate threshold; “self-improving” agents that write unconditionally tend to drift, not learn.

Key Research: Reflexion (Shinn et al., 2023) — verbal reinforcement · VOYAGER (Wang et al., 2023) — skill libraries (procedural memory)

Fine-Tuning vs Procedural Memory

Fine-Tuning Procedural Memory
Mechanism Updates model weights Injects a playbook into the prompt
Setup Slow, offline, requires labeled data Fast, online, autonomous
Reversibility Hard Trivial (delete the memory)
Per-user customization Expensive Free

. . .

TipIn-Context Learning Wins for Personalization

Fine-tuning is right for global behavior changes. Procedural memory is right when the “right” approach varies per user, per task, or per week.

ImportantNever Block on Memory Writes

Memory generation costs an LLM call. Blocking the user’s reply on it adds 1–3 seconds of pure latency for no user-visible benefit.

Production Concerns

Concern What to do
Concurrency Optimistic locking on per-memory updates; queue heavy generation
Failure handling Retry with exponential backoff; dead-letter for repeated failures
Multi-region Memory store needs replication — consolidation requires consistent reads
Privacy Per-user ACLs; PII redaction before persistence; opt-out for memory generation; honor delete-on-request (GDPR-style targeted erasure of a user’s memories)
Memory poisoning Malicious user input → “fact” extracted → poisons future turns. Sanitize at write time.
Embedding drift Stored vectors go stale if you change the embedding model — keep the embedder versioned, and re-embed the store on upgrade

Evaluation: Measure the Lift, Not the Fact Count

You already have the eval machinery from RAG evaluation — memory reuses all of it:

  • Extraction is graded like generation — precision / recall of captured facts vs a golden set
  • Retrieval is graded like RAG — Recall@K, latency

. . .

But those are leading indicators. The headline question is whether memory changes outcomes:

Measure memory by task-success lift — not by counting facts.

. . .

Evaluation: Ablation vs. A/B Testing

Prove it once, then A/B the config

Memory isn’t free — tokens, latency, poisoning, over-influence — so the lift is not guaranteed.

  1. Justify it once with a memory-on vs memory-off ablation: replay your golden sessions with the pipeline wired in vs stubbed out.
  2. After that, on/off retires. A/B the configuration instead — injection placement, recency/importance weights, extraction cadence.

Observability & Evaluation will frame Task Success Rate as the headline agent metric; this is its memory-specific instance.

H. Wrap-up

Key Takeaways

  1. LLMs are stateless. Context Engineering is the discipline of building the right payload every turn.
  2. Sessions = one conversation, events + state, persisted in a durable store.
  3. Context Windows are expensive and performance-bound—be strategic about what you include.
  4. Compact what you send, not what you store. Sliding window, token cap, recursive summary.
  5. Memory = cross-session, distilled. Declarative for facts, procedural for playbooks.
  6. Memory pipeline = extract → consolidate (CREATE/UPDATE/DELETE) → store → retrieve.
  7. Always async, always isolated, always evaluated.
