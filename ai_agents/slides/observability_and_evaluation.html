Traditional vs Agent Debugging

🖥️ Traditional Debugging

  • Same input → same output
  • Stack trace shows exact failure
  • Unit tests with assertEqual
  • Fixed cost per execution
  • Errors crash the program

🤖 Agent Debugging

  • Same input → different outputs
  • Failure emerges over many steps
  • Subjective quality evaluation
  • Variable cost (1–50 LLM calls)
  • Errors silently “reasoned away”

The Core Problem

An agent might technically succeed (no crash, produces an answer) while being completely wrong. Or it might spend $0.50 on a $0.02 question. You can’t fix what you can’t see.

The Four Pillars of Agent Quality

🎯 Effectiveness Did it achieve the user’s intent?

  • Conversion vs. Task Success
  • Result quality & accuracy
  • Goal alignment

⚡ Efficiency Did it solve the problem well?

  • Token consumption & Latency
  • Trajectory length (Step count)
  • Cost-to-value ratio

🛡️ Robustness How does it handle adversity?

  • Graceful failure vs. Hallucination
  • API timeouts & missing data
  • Edge case handling

🔒 Safety & Alignment The non-negotiable gate.

  • No data leakage
  • Refusing harmful instructions
  • Staying within persona

Outside-In: Black Box → Glass Box

A two-stage diagnostic process.

📦 Black Box (Outside-In)

“Did the agent achieve the goal?”

  • KPIs: Success Rate, CSAT
  • Output: Final response quality
  • Decision: If Yes, done. If No, open the box.

🔬 Glass Box (Inside-Out)

“Why did it fail?”

  • Trajectory: Step-by-step logic
  • Tools: Params & Response handling
  • RAG: Retrieval performance
  • Orchestration: Multi-agent dynamics

“Move from ‘the final answer is wrong’ to ‘it’s wrong because…’ That diagnostic power is the entire goal of agent evaluation.”

How Agents Fail: Acute vs Chronic

🔥 Acute Failures
Visible immediately in a single run

  • 🤔 Ambiguity — Misunderstood task
  • 🔧 Misuse — Wrong tool/arguments
  • 🔁 Infinite Loops — Spinning in circles
  • 💬 Hallucination — Confident lies

→ Solved by Per-Run Tracing

📉 Chronic Failures Invisible in any single run

  • ⚖️ Bias — Operationalized training biases
  • 🌍 Drift — Performance decay over time
  • 🤖 Emergence — Unexpected “proxy wars”
  • 🔇 Regression — Prompt edits tanking quality

→ Solved by Aggregated Eval

Classifying Tool Errors

Not every failure is the model’s fault. Mixing them is what turns dashboards into noise. Cursor’s three-bucket taxonomy:

Category Whose fault? Example Treat as
Invalid arguments Model Wrong types, hallucinated fields, bad schema Glass-box quality bug
Unexpected environment Model Right tool, right shape — but file missing, no permissions, stale state Glass-box quality bug
Provider error Infrastructure 5xx from the LLM provider, rate limit, dependency timeout SLO / operational issue

Why the split matters

The first two are training and prompt signal — they say “the agent is using the harness wrong” and feed into your eval set. The third is operational signal — it pages SRE. Conflating them means real quality regressions get drowned in flaky provider noise.

Same model, 10× fewer tool errors

Cursor reports a 10× reduction in tool-error rate from harness-side tuning alone — no model change. The taxonomy is what makes that improvement measurable.

B. Structured Tracing

Every step, captured and queryable

What a Good Trace Captures

For every step in the agent loop:

📍 Identity

  • Unique Trace ID per request
  • Step number
  • Agent name & model

📊 Metrics

  • Token usage (input / output)
  • Cost per step (USD)
  • Duration (milliseconds)

📝 Content

  • Agent’s reasoning (LLM response text)
  • Tool calls (name + arguments) + Tool results

A Trace Data Model

@dataclass
class ToolCallRecord:
    tool_name: str
    tool_input: dict
    tool_output: str
    duration_ms: float

@dataclass
class AgentStep:
    step_number: int
    reasoning: Optional[str]
    tool_calls: list[ToolCallRecord]
    input_tokens: int = 0
    output_tokens: int = 0
    cost_usd: float = 0.0

@dataclass
class Trace:
    trace_id: str
    agent_name: str
    steps: list[AgentStep]

    total_cost_usd: float = 0.0

Enriching Traces with Context

The propagate_attributes context manager allows you to inject rich metadata without polluting your function signatures.

    # 1. Propagate metadata and tags to this span and its children

C. Loop Detection

Catching agents that spin in circles

The Infinite Loop Problem

An agent calls search("python tutorial"), gets a result, then calls search("python tutorial") again. And again. And again.

Why it happens:

  • Doesn’t “understand” the result satisfied the query
  • Tool returns an error → retries same args
  • Ambiguous prompt → keeps trying variations

💸 Cost Impact

A looping agent can burn through hundreds of API calls at $0.01–0.05 each.

Idempotent vs Polling Tools

Two retry behaviors — same syntax, opposite meaning.

🔁 Idempotent

Same call → same result. Calling twice is equivalent to calling once.

  • search("python tutorial")
  • read_file("/etc/hosts")

→ Safe to retry on failure. Repeating with identical args is a red flag — the agent is likely stuck.

⏱️ Polling

Same call → different result over time. Repetition is the whole point.

  • get_job_status(job_id)
  • check_payment_status("txn_42")

→ The agent is expected to call this repeatedly until state changes.

Schema Design Connection

We must hint this retry behavior in the tool’s schema description (Schema Design) so the loop-detection logic can distinguish a stuck agent from a legitimate poll.

Three Detection Strategies

Loops appear in two places — we need a different check for each:

Tool-Call Checks — before each tool executes

  1. Exact Match — same tool + identical args
  2. Fuzzy Match — same tool + suspiciously similar args

Reasoning Check — after each LLM response

  1. Output Stagnation — the agent keeps saying the same thing

Strategy 1: Exact Match

Same tool + identical arguments repeated N times.

# Before executing each tool call:
count = tool_history.count(
    (current_tool_name, current_args_string)
)

if count >= exact_threshold:
    return LoopDetected(confidence=1.0)

tool_history.append(
    (current_tool_name, current_args_string)
)

✅ Confidence: 100%

If the tool is idempotent (like a search), same call twice = always a loop.

Polling Exception

For tools like check_job_status, repeating calls are expected. Skip exact match detection for polling tools.

Strategy 2: Fuzzy Match — Concept

Similar (but not identical) tool calls — catches minor rephrasing.

We compare argument strings only (not the tool name), tokenised into word sets:

Jaccard(A, B) = |A ∩ B| / |A ∪ B|

# Call 1: search("Paris population")
args_A = {Paris, population}

# Call 2: search("population of Paris")
args_B = {population, of, Paris}

Intersection = {Paris, population}        → 2
Union        = {Paris, population, of}    → 3
Jaccard = 2/3 = 0.67  ← Suspicious 🚩

How Jaccard works

Count the shared words divided by the total unique words across both sets.

A score near 1.0 = almost identical. A score near 0.0 = completely different.

Strategy 2: Fuzzy Match — Threshold

Does this catch genuinely different queries too? Let’s check.

# A genuinely different call for comparison:
args_A = {how, to, code, python}          → search("how to code python")
args_B = {python, programming, tutorial}  → search("python programming tutorial")

Intersection = {python}                   → 1
Union        = {how, to, code, python,
                programming, tutorial}    → 6
Jaccard = 1/6 = 0.17  ← Different query ✅

Threshold: 0.8

  • 0.67 (“Paris” rephrasing) → below threshold, but high enough to log a warning
  • 0.17 (different topic) → safely ignored
  • Set it at 0.8 to catch true rephrasings without flagging adjacent queries.

Strategy 3: Output Stagnation

A different kind of loop

Strategies 1 & 2 detect repeated tool calls. Stagnation detects when the agent’s reasoning text is stuck — it runs after each LLM response, not before tool execution.

What it looks like:

Step 4: "I need to search for more info..."
Step 5: "I need to search for more info..."
Step 6: "I need to search for more info..."

The agent keeps producing nearly identical reasoning, even if it issues different tool calls.

How we detect it:

After each LLM response, we add the text to output_history.

We then compute the average word overlap across the last N entries — a high score means the agent is thinking in circles.

recent_outputs = output_history[-stagnation_window:]

if avg_pairwise_word_overlap(recent_outputs) >= threshold:
    return LoopDetected(strategy="stagnation")

The Circuit Breaker Pattern

Combine loop detection with the agent loop to break infinite cycles:

for step in range(max_steps):
    # ... get LLM response, extract tool calls ...

    for tool_call in tool_calls:
        # Check BEFORE executing
        loop_check = loop_detector.check_tool_call(
            tool_call.name, str(tool_call.arguments)
        )

        if loop_check.is_looping:
            # Inject warning into conversation instead of executing
            messages.append({
                "role": "tool",
                "content": f"LOOP DETECTED: {loop_check.message}"
            })
            break  # Skip remaining tool calls this step

Tip

The agent receives the loop warning as if it were a tool result — it can then change strategy on the next step.

Monitoring spend per query

Why Track Cost?

  • “Some queries are expensive but we don’t know which”
  • No budget enforcement
  • Runaway agents go undetected

✅ With tracking:

Budget Guardrails

Enforce per-query and daily limits.

from datetime import date
from threading import Lock

from src.exceptions import TokenBudgetExceeded

class BudgetGuard:
    """Enforce daily API spend limits."""

    def __init__(self, daily_limit_usd: float):
        self.daily_limit = daily_limit_usd
        self._daily_spend: dict[str, float] = {}
        self._lock = Lock()

    def check_and_charge(self, cost_usd: float) -> bool:
        """Returns True if allowed, raises TokenBudgetExceeded otherwise."""
        with self._lock:
            day_key = date.today().isoformat()
            day_spend = self._daily_spend.get(day_key, 0)

            if day_spend + cost_usd > self.daily_limit:
                raise TokenBudgetExceeded(f"Daily budget ${self.daily_limit} reached")

            self._daily_spend[day_key] = day_spend + cost_usd
            return True

Derive Your Own Metric: Cursor’s Keep Rate

Benchmarks measure a frozen task set. Real production demands a metric tailored to your product’s actual value.

Goodhart’s Law — “when a measure becomes a target, it ceases to be a good measure.” Public benchmarks (MMLU, SWE-bench) saturate and get gamed once labs optimize for them — which is exactly why you need a product-specific metric they can’t train against.

Case Study: Cursor’s “Keep Rate”

\[\text{Keep Rate} = \frac{\text{Agent-generated code remaining in codebase after interval } \Delta t}{\text{Total agent-generated code inserted}}\]

User keeps it → Keep Rate goes up. User deletes or rewrites it → Keep Rate drops. This measures what survives contact with the user.

🧪 Lab Benchmarks
e.g., SWE-bench / TaskCompletion

Did the agent produce a passing output in the static lab environment?

🚀 Derived Production Metrics
e.g., Keep Rate

Did the agent produce work the user actually shipped, kept, and built upon?

Generalizing: Find Your “Keep Rate”

The key to a production metric is measuring post-action retention or behavior instead of static outputs. What is your agent’s equivalent?

💻 Coding & Chat Agents

  • Coding Agents: Keep rate (code edit retained in repo after \(N\) days)
  • Chat Agents: Suggestion-followed rate / thumbs-up 👍 ratio

⚙️ Workflow & Draft Agents

  • Workflow Agents: Task-not-redone rate (does a human repeat/fix the step?)
  • Email / Draft Agents: Edit-distance from agent draft to final sent version

Crucial Agent Takeaway

This custom, product-specific metric is the agent analogue of standard quality alerts. Once defined, it becomes the north-star metric that your training, prompts, and orchestration/harness should continuously optimize toward.

Sampling & Privacy in Production

📊 Dynamic Sampling — the 10/100 rule

Full traces on every request is prohibitively expensive and adds latency. Instead:

  • DEBUG-level traces in development
  • INFO-level + sampling in production:
    • Trace 10% of successful requests
    • Trace 100% of all errors

Statistical visibility on the happy path. Full diagnostic detail on every failure.

🔐 Privacy Warning

User inputs in traces often contain PII (Personally Identifiable Information). Scrub before long-term storage — once it lands in a store, you’ve created a compliance problem.

→ See Guardrails — PII redaction (Presidio + regex).

From Traces to Test Cases

The previous slide’s 10/100 sampling gives you a representative trace pool. The next question: how does that pool become an eval dataset?

Reuse the 10/100 pool — same data, new purpose. The previous slide gathered it for observability; here we curate it for evaluation.

  • Semantic deduplication — real users ask the same question thousands of times. Cosine similarity above ~0.9 between query embeddings collapses near-duplicates, so your eval set keeps boundary cases, not popularity. Treat the threshold as a starting heuristic, not a constant.
  • PII scrubbing — same constraint as tracing. Route mined traces through Guardrails — PII redaction (Presidio + regex) before they land in your committed dataset.

Synthetic vs. mined

Hand-written test sets drift from production. Mined cases stay honest — and every new user query becomes a candidate test case.

F. Evaluating Quality with DeepEval

Production metrics catch system problems. Now we need offline checks that catch quality regressions before they ship.

The Evaluation Problem

How do you know if your agent is any good?

  • ❌ Manual review doesn’t scale
  • ❌ String matching can’t evaluate free-text
  • ❌ Unit tests check format, not quality
  • ❌ Custom LLM judges are hard to calibrate

✅ The Solution: DeepEval

An open-source framework with 50+ research-backed metrics for LLM and agent evaluation.

Integrates with pytest for CI/CD (Continuous Integration / Continuous Deployment) workflows.

Why DeepEval for Agents?

❌ Traditional Metrics Fail

Metric Problem
BLEU/ROUGE Word overlap, not meaning
Accuracy Binary, no nuance
Precision/Recall Not for open-ended output

✅ DeepEval Approach

  • LLM-as-a-Judge with calibrated prompts
  • Agentic metrics: task completion, tool correctness
  • Component-level evaluation via tracing

Metric What It Measures Mode

A Step Toward Agent-as-Judge

Traced metrics evaluate the trajectory, not just the final answer — a step toward Agent-as-a-Judge (Zhuge et al., 2024).

What full Agent-as-Judge adds

A full Agent-as-Judge goes further: the judge itself uses tools to verify each step — re-run a search, check a fact, inspect intermediate state — instead of trusting the trace at face value.

Traces & Spans

One user query = one Trace. Each step inside it = a Span.

📦 Trace — the whole journey

Receipts for an entire shopping trip.

One per request · unique ID · contains many spans.

🔬 Span — one step of the journey

One item on the receipt.

One LLM call / tool / function · records timing, inputs, and outputs · nested under a parent.

Unified Tracing with @observe

@observe is the standard pattern for leading tracing libraries like Langfuse and DeepEval. The decorator surface is near-identical — only the keyword name differs:

# Pick your vendor; the lab uses SimpleObserver which mirrors both.
from langfuse import observe         # ➜ @observe(as_type="agent")
from deepeval.tracing import observe # ➜ @observe(type="agent")

@observe(as_type="agent")  # or type="agent" for DeepEval
async def run(self, query):
    ...
    return answer

Same shape, different kwarg. Code written against one library transfers with a single keyword change (as_type vs type).

The CRUD Challenge

You cannot run execute_payment against prod during nightly eval

Replay-style evaluation works for read-only agents. For agents with mutating tools, naive replay corrupts state — and skipping the tool changes what the agent sees mid-trajectory, so you’re no longer testing the same agent.

The problem

  • Tools may CREATE / UPDATE / DELETE state — payments, user records, file writes
  • Re-running the trace mutates production again
  • Skipping the tool breaks the trajectory the agent is supposed to navigate

Mitigations

  1. Tag tools — label passive (search, retrieval) vs active (CRUD) in trace metadata; handle them differently in the harness
  2. Snapshot tool I/O in traces — record the actual response at runtime, replay from the snapshot during eval (no live call)
  3. Timestamped DB queries for retrieval agents — pin the corpus to the moment the trace ran so index drift doesn’t skew scores
  4. Mock APIs — dedicated isolated endpoints for genuine mutations that can’t be snapshotted

Important

This is why your tracer must capture tool inputs and outputs verbatim (recall section B’s ToolCallRecord). Your eval harness depends on those snapshots.

Three Tiers of Evaluation

Different failure modes deserve different evaluators. Use the cheapest tier that catches the failure.

Tier Cost Speed Best For
String / embedding
(ROUGE, BERTScore)		 $ Fast Retrieval relevance, regression trends
LLM-as-a-Judge $$$ Slow Plan quality, summary fidelity, tone
Human review $$$$ Slowest Nuanced ethics, domain accuracy, golden-set creation

Trend over absolute

A specific BERTScore of 0.8 doesn’t mean the answer is “good”. Real value is in tracking changes — if main averages 0.8 and a new commit drops it to 0.6, you’ve automatically detected a regression.

Pairwise LLM Judging Beats Absolute Scoring

❌ Absolute Scoring (1–5)

Noisy, subjective, and hard to calibrate.

Moving an average from 3.8 to 4.0 is often just noise — within LLM judge variance. It’s too easy to “game” the numbers.

✅ Pairwise Comparison

Binary choice forces a definitive signal.

Forces a head-to-head choice. Aggregate to a win / loss / tie rate. A high win rate is the most reliable signal of improvement.

Workflow: v1 vs v2 → “New agent wins 67% of battles” 🏆

Evaluate which response is more helpful:

[Query] "My order #12345 hasn't arrived."

[A] "Out for delivery, arrive by 5 PM."
[B] "On the truck. Be there by 5."

Compare correctness and tone. 
Return JSON: { "winner": "A"|"B"|"tie", "rationale": "..." }

It is far easier for an LLM to decide “A > B” than to decide if A is exactly a “4” or a “5”.

Aggregating these head-to-head wins into a ranking is Elo / arena-style scoring — the same approach LMSYS Chatbot Arena uses to rank frontier models.

The SME-to-Judge Pipeline

Before we can calibrate a judge, we need a high-quality rubric. But where does that rubric come from?

Domain experts (lawyers, support leads, ops) hold the ground truth — but they aren’t prompt engineers. Bridge the gap with a structured pipeline:

Four practical rules

  1. Forced justification on 👎 — never ship a thumbs-down without a mandatory text reason. “It cited the 2023 return window instead of the 2024 policy.”
  2. Justification clustering — LLM-summarize SME comments into recurring failure categories
  3. Rubric co-design — convert each category into a binary judge question. “Does the response reference the 2024 policy window? Yes/No”
  4. Human few-shots — embed the actual SME-labeled traces with their written rationales as few-shots in the judge prompt

With SME-anchored rubrics in hand, the judge has something concrete to calibrate against →

Calibrating the LLM Judge — The Loop

Calibrate against expert labels before trusting the judge to gate releases.

Calibration loop — the judge’s “training loop”:

  1. Curate 100–300 tricky I/O pairs (boundary cases, hallucinations)
  2. Label with experts using the target rubric
  3. Iterate prompt — clarify rubric, add few-shots, use other techniques…
  4. Re-score until LLM judge–human agreement is reached

Measure agreement:

  • Spearman’s ρ — for ordinal scores (1–5 ratings)
  • Cohen’s κ — for categorical labels (pass/fail, A/B/tie)

15–20% rule: if the judge disagrees with humans on more than 15–20% of cases, the prompt is unstable — keep iterating before CI.

Calibrating the LLM Judge — Reading Agreement

ρ / κ Interpretation
> 0.8 Ready to gate releases
0.6–0.8 Workable, watch edges
0.4–0.6 Iterate rubric & few-shots
< 0.4 Rethink the metric

Table values are chance-corrected (κ / ρ). The 15–20% rule on the previous slide is raw agreement — a cheaper screening check, not the release gate.

ML Analogy: calibration set ≈ training set · prompt + rubric ≈ weights · agreement ≈ validation loss · golden dataset ≈ held-out test set.

LLM Judges in Production — Biases & Mitigations

A calibrated judge is necessary but not sufficient. Production pipelines wrap it with bias mitigation before trusting any score.

⚠️ Common biases & their fixes

  • Positional — favors whichever answer comes first → swap and aggregate
  • Verbosity — rewards long answers → state in rubric that length ≠ quality
  • Self-preference — prefers its own model family → committee of 3 judges, take median
  • Silent failures — require rationale before score
# Mitigate positional bias
score_AB = judge(q, A, B)
score_BA = judge(q, B, A)  # swap
final    = aggregate(score_AB, score_BA)

LLM Judges in Production — The Golden Dataset

The other half: a frozen test set that the judge is never calibrated against.

📚 The Golden Dataset

200–500 human-verified examples covering common queries, known regressions, and adversarial cases.

Treat it as a held-out test set — never calibrate the judge against it.

How it gates CI

  • Every Pull Request (PR) runs the calibrated judge against the Golden Dataset
  • Track per-metric baselines; a drop (e.g. faithfulness 0.9 → 0.8) blocks the merge
  • Surface the judge’s rationale on failure — engineers debug fast

G. Closing the Loop: The Quality Flywheel

The Agent Quality Flywheel

Evaluation is not a one-off — it’s a self-reinforcing system. Four phases, looping forever:

Concrete loop in practice

Production trace → user clicks 👎 → review queue → human annotates → appended to test_cases.json → fails CI on next run until fixed.

Every production failure becomes a permanent regression test. This is how you catch the chronic failures from Section A — drift, bias, silent regression — that no individual run will ever reveal.

H. Wrap-up

Key Takeaways

Observability

  1. Four Pillars frame quality: effectiveness, efficiency, robustness, safety
  2. Acute vs Chronic failures need different defenses
  3. Tracing is non-negotiable — Glass Box opens only when Black Box fails
  4. Loop detection + budget guards stop runaway agents

Evaluation

  1. System vs Quality dashboards serve different teams
  2. Three tiers — string → LLM-judge → human; use the cheapest that catches the failure
  3. Pairwise judging beats absolute 1–5 scoring
  4. Flywheel + Human-in-the-Loop (HITL) turn every failure into a permanent regression test with LLM judges
