Recall: Separate Histories Need a Contract

In Patterns of Collaboration we split one agent into a team. When specialists keep separate, private histories, only their outputs cross — and that hand-off needs a contract.

So far every specialist has lived in your process: same codebase, same runtime, same memory. This session asks the next question:

What if the specialist isn’t yours?

What if the best “Real-time Compliance” or “Logistics” agent was built by another team — in another language, on another framework, running on another machine?

Internal vs. Distributed

Internal sub-agents (Session 1)

  • Share one runtime and memory
  • In-process function calls
  • Low latency, simple state
  • You own and maintain all of them

Distributed agents

  • Live across network boundaries
  • Built by different teams / frameworks / languages
  • Communicate over the wire
  • You consume them, you don’t own them

The moment a specialist crosses a network boundary, “just call the function” stops working. You need a shared protocol.

The Fragmentation Tax

You could hand-build a wrapper for every external specialist — a custom subagent for Salesforce, another for ServiceNow, another for an internal HR system.

  • Each speaks a different payload shape, transport, and auth scheme
  • Each upstream API change breaks your bespoke bridge — a permanent maintenance tax
  • “Build vs. buy”: every wrapper you own is leverage you don’t spend on your actual product

This is the same N×M problem MCP solved for tools (MCP & Standardization) — now one level up, for agents.

Tool vs. Collaborator: The GOTO Problem

Why not just wrap a remote agent as one more tool?

A tool is fire-and-forget

  • Bounded domain
  • One well-formed request → one response
  • No memory of the exchange

An agent is a collaborator

  • Unbounded domain — crooked walls, ambiguity
  • May pause, ask for clarification, resume
  • Carries multi-turn state

The GOTO problem

Force a collaborator into a fire-and-forget tool wrapper and control flow can leave and never cleanly return — the agent stalls waiting for input your orchestrator never expected to give. We need a protocol built for pausing, negotiating, and resuming.

B. A2A — Agent-to-Agent

A lingua franca for agents across boundaries

A2A: The Standard for the Virtual Workforce

A2A is an open protocol for one agent to discover and delegate to another — agnostic to how each was built.

  • Introduced by Google (2025); donated to the Linux Foundation — vendor-neutral governance
  • Backed by 150+ organizations (Microsoft, AWS, Salesforce, SAP, ServiceNow, …)
  • Abstracts away transport, framework, language, and payload differences

Just as HTTP standardized the web, A2A standardizes the virtual workforce — your orchestrator can “hire” any A2A-compliant specialist, anywhere.

The Agent Card

Every A2A agent publishes an Agent Card — the machine-readable “CV” of the AI world:

Field What it declares
Capabilities / Skills What tasks the agent can perform
Service endpoint Where to reach it
Auth requirements How to authenticate
Interaction schemas How to talk to it over A2A

Convention: served at https://<host>/.well-known/agent-card.json, so any client can discover an agent the way browsers discover a site’s metadata.

Discovery: Registries

Once an agent has a card, it becomes a discoverable service in a registry:

Public marketplaces

  • A global “talent agency” of agents
  • List a specialist; license it to thousands of orchestrators

Private enterprise registries

  • Governed, internal catalog
  • Share a specialist across departments without leaving the security boundary

Same pattern, one level up

Public / managed / private — the same trust hierarchy as MCP server discovery. Prefer governed registries in production.

Two Motions: Expose & Connect

Expose (supply side)

  1. Define the Agent Card
  2. Add an executor — translates A2A requests into your framework’s calls
  3. Publish an A2A endpoint

Connect (demand side)

  • Direct — point at a known endpoint
  • Via registry — discover, then resolve the endpoint dynamically

C. A2UI — Agent-to-UI

Agents that return interface, not JSON

The Communication Gap

Ask a colleague “How did Q4 perform by region?” and they sketch a chart and circle the outliers. They don’t hand you a spreadsheet.

Yet agents return raw JSON — and you build the chart: import a library, configure axes, manage state. That context-switch breaks the flow.

A2UI lets an agent return a complete, interactive interface as its output — not just data.

A2UI: Declarative UI Intent

Running LLM-generated code in your app is a security nightmare (injection, XSS). A2UI avoids it entirely:

  • The agent emits declarative UI intent — a portable JSON description of what to render, not executable code and not fixed pixels
  • The client renders it using its own trusted component catalog (React, Flutter, Lit, Angular…)
  • The catalog defines what’s available; the agent only composes from it

Sheet music, not a recording

The agent writes the score (intent); each client’s renderer “plays” it natively. Because the agent can only reference catalog components, it cannot inject arbitrary code — that separation is what makes it safe.

Two Patterns — and When

LLM generates the UI (default)

  • Model owns the layout, adapts to intent
  • “Compare these regions” and “show trends” get different interfaces
  • Flexible, conversational

Tool returns a fixed UI (template)

  • One tool call, no tokens spent on layout
  • Fully predictable output
  • Best when the layout is deterministic from inputs

Pick by who owns the layout

Intent-driven (LLM) when the view should adapt; input-driven (template) when every dashboard should look identical. Emerging standard — Google open project, stabilising through 2026.

D. Agent Commerce

UCP & AP2 — the brain and the wallet

From Reading to Spending

MCP, A2A, and A2UI are mostly about reading and reasoning. The next frontier is agents that take actions with real-world financial weight.

A different risk class

You won’t paste your card number into a prompt and say “go wild.” Commerce needs authorization, auditability, and hard guardrails — exactly the concerns from the security module.

UCP & AP2: The Brain and the Wallet

Your AI orders dinner for the apartment. Two protocols split the job:

UCP — Universal Commerce Protocol

The brain: discover, cart, order.

  • “The HTTP of commerce” — every merchant publishes menu, options, and pricing in one machine language
  • Standard schemas: discover products → build cart → track order

AP2 — Agent Payments Protocol

The wallet: pay, safely.

  • Three signed Mandates: Intent (what you want) → Cart (what the agent assembled) → Payment (what gets charged)
  • A cryptographic “permission slip” proving a human approved this purchase

Guardrail in action: you sign “up to $25 at the taco place.” The agent presents a signed mandate for an $18.50 order — try to charge $50 and the protocol rejects it.

How Settlement Happens

UCP AP2
Role Decides what to buy, builds the cart Handles how to pay, without leaking card details
Integrates with Any merchant / business provider Payment networks
Guarantees Unified schema, discovery Authorization, auditability, accountability

Related: x402

A complementary settlement path revives the long-dormant HTTP 402 “Payment Required”: the server returns a price, the agent pays (often stablecoins) and retries with cryptographic proof — machine-to-machine, no human in the loop. Emerging; AP2 announced Sept 2025, UCP early 2026.

E. Wrap-up

The Interoperability Stack

One orchestrator, four open standards — tools, agents, interface, and commerce.

From Builder to Orchestrator

Standard Connects you to Maturity
MCP Tools & data sources Established
A2A Other agents (the virtual workforce) Established, 150+ orgs
A2UI Human users, via generative UI Emerging (2025–26)
AP2 / UCP Merchants & payment rails Emerging (2025–26)

The thesis

Adopting open standards moves you from wiring fragile bespoke bridges to orchestrating high-value intent. Spend your tokens on the product, not the plumbing.

Key Takeaways

  1. Distributed ≠ internal — once a specialist crosses a network boundary, you need a protocol, not a function call
  2. A2A standardizes the virtual workforce — Agent Cards, registries, expose & connect
  3. Tool vs. collaborator — fire-and-forget vs. multi-turn negotiation (the GOTO problem)
  4. A2UI returns interface, not JSON — safe because it’s declarative, not executable
  5. Commerce needs guardrails — UCP is the brain, AP2 the cryptographically-signed wallet
  6. Verify before you build on it — A2A is established; A2UI/AP2/UCP are emerging and moving fast
