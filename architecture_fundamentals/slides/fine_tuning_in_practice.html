Method Map — Two Independent Choices

Fine-tuning is two decisions, not one. Mix and match.

Common combinations Typical use
SFT via QLoRA The default open-source workflow (single consumer GPU)
SFT via Full FT Frontier teams with big clusters and large datasets
SFT → then DPO, both via LoRA Teach format first, polish preferences after

The taxonomy in one line

Objective = SFT or DPO (what loss are you minimizing?). Parameterization = Full / LoRA / QLoRA (how many weights move and at what precision?). Pick one from each column.

SFT — Supervised Fine-Tuning

The default starting point. You give the model a dataset of (prompt, ideal_response) pairs and it learns to imitate.

{"messages": [
  {"role": "system", "content": "You are a Saudi legal assistant."},
  {"role": "user", "content": "What are the requirements for a commercial lease?"},
  {"role": "assistant", "content": "Under Article 5 of the Commercial Court Law..."}
]}
  • Loss function: standard next-token prediction, computed only on the assistant tokens.
  • What it teaches: style, format, structural patterns, vocabulary.
  • What it can’t teach well: “be helpful but refuse if X” — preference rules with no single correct output.

DPO — Direct Preference Optimization

For “prefer A over B” learning. Your dataset is triples of (prompt, chosen_response, rejected_response).

{
  "prompt": "Explain BM25 to a junior engineer.",
  "chosen": "BM25 is a ranking function that scores documents by...",
  "rejected": "BM25 stands for Best Matching 25 and is used in..."
}

Why not RLHF?

DPO is a popular alternative to RLHF — same goal (align to preferences), but it removes the separate reward-model training stage. Many open-source teams skip RLHF in favor of DPO for that simplicity, though whether DPO actually matches PPO-based RLHF on hard preference tasks is still debated (see the “Open question” in Further reading).

  • What it teaches: which of two valid responses is better — tone, helpfulness, refusal patterns.
  • When to use: after SFT, when the model already speaks the right format and you’re polishing.

LoRA / PEFT — Parameter-Efficient

Instead of updating all ~7B weights, freeze them and inject small trainable adapter matrices into each attention layer.

The math in one line

Replace W ← W + ΔW with ΔW = B · A where B ∈ ℝ^(d×r), A ∈ ℝ^(r×k), and r ≪ d. You train A and B only — two skinny matrices instead of one wide one. The product is low-rank, which is the whole point: capacity-limited so the base model’s general knowledge survives.

Full fine-tuning

  • Updates ~7B parameters
  • Needs ~80GB VRAM for a 7B model
  • ~$50–500 per training run
  • Produces a new full model (~14 GB)

LoRA

  • Updates ~10M parameters (0.1%)
  • Runs on a single 24GB GPU
  • ~$5–50 per training run
  • Produces an adapter file (~50 MB)

Picking r and alpha

  • r (rank) controls capacity. r=8 for narrow style/format tasks, r=16 is the default, r=32–64 for harder behaviors. Bigger r ≠ better — small r is often a feature (resists overfitting).
  • lora_alpha is a scaling factor. Convention: alpha = 2 · r. The effective update is scaled by alpha / r, so this keeps the step size constant as you sweep r.
  • target_modules = which projections get adapters. ["q_proj", "v_proj"] is the LoRA-paper default; ["q_proj","k_proj","v_proj","o_proj"] is more thorough and now common.

The adapter shipping pattern

Keep the base model on disk once. Ship adapters per use-case (legal, medical, customer-service) and hot-swap them per request — same VRAM, many models.

B. Dataset Preparation

The 90% of the work nobody shows in tutorials

What Good Data Looks Like

Dimension What “good” means
Size 500-5K examples for narrow tasks; more is rarely needed for SFT/LoRA. Quality > quantity.
Diversity Cover the full input distribution you’ll see in production. No 90% one template.
Consistency Every example follows the same answer style. Inconsistency teaches the model that anything goes.
Cleanliness No PII, no broken Unicode, no truncated answers. The model will learn the trash too.
Provenance You know where each example came from. Lets you remove a source if it turns out poisoned.

The dataset is the spec

The model will learn whatever pattern is most consistent across your examples — including patterns you didn’t intend. Mislabel 5% of examples and you’ve trained that mistake in.

From Raw Transcript to One SFT Row

What “curate one example” actually looks like.

Raw support transcript

[2026-04-12 14:32] Customer: hi my order
hasnt come yet its been like 8 days???
order # is 4471

[14:33] Agent: Hi! Let me check that for

[14:35] Agent: I see your order shipped
on the 5th but the carrier had a delay.
It's now out for delivery today. You'll

Noisy, real, full of timestamps and chat artifacts.

Cleaned SFT row

{"messages": [
  {"role": "system",
   "content": "You are a polite, concise
shipping support agent. Always confirm the
order number and give a clear next step."},
  {"role": "user",
   "content": "My order #4471 hasn't
arrived after 8 days."},
  {"role": "assistant",
   "content": "Order 4471 shipped on the
5th; the carrier was delayed. It's out for
delivery today and will arrive by 6 PM."}
]}

Stripped, restructured, written in the voice you want the model to learn.

What you did in this transformation

Picked a system prompt, removed timestamps, merged the agent’s two turns into one, and rewrote in clean grammar. Every choice here teaches the model a behavior. Do this 500 times and you have a dataset.

Common Sources

  1. Human-written from scratch — gold standard, slowest, $5-50 per example.
  2. Frontier-model distillation — Claude/GPT-4 generates candidates; humans curate. ~10x faster.
  3. Real production logs — your existing system’s outputs, after heavy filtering. Free, but biased toward what already works.
  4. Public datasets — Alpaca, Dolly, OASST. Useful for general capabilities; rarely fits a specific business task.
  5. Synthetic — programmatically generated. Cheap; risks teaching synthetic-looking patterns.

Distillation ToS warning

Provider terms commonly restrict using their model outputs to train models that compete with theirs — but the specifics shift. OpenAI relaxed parts of this restriction in 2024; Anthropic’s commercial terms remain stricter. “Distilling GPT-4 into a 7B” may be fine today and prohibited tomorrow, or vice versa. Always read your provider’s current terms (and get legal review) before scaling a distillation pipeline for a commercial product.

A realistic pipeline

Start small: 200 examples hand-curated, then evaluate. If the eval moves, scale to 2K. If not, your problem isn’t dataset size — it’s task definition or model choice.

Train / Validation Split

from sklearn.model_selection import train_test_split

train, val = train_test_split(dataset, test_size=0.1, random_state=42)

# Critical: hold out an additional **eval set** the training loop never sees.
# This is what you report final numbers on.

Three buckets, not two

  • Train (~80%) — the model sees this during training
  • Validation (~10%) — checked every epoch to spot overfitting
  • Eval / test (~10%) — held out for the final report card; never touched until the end

The Chat-Template Trap

Day-one mistake nobody warns you about

Every instruction-tuned model has a chat template — the exact tokens that wrap system/user/assistant turns (<|im_start|>, [INST], <|begin_of_text|>, etc). If your training data doesn’t match it, the model unlearns the template and behaves erratically at inference.

# Right way — let the tokenizer do it
text = tokenizer.apply_chat_template(
    example["messages"],
    tokenize=False,
    add_generation_prompt=False,
)
# `text` now has the exact special tokens Llama-3.1 / Qwen / Mistral expects.

Three rules:

  1. Use tokenizer.apply_chat_template — never hand-roll the template.
  2. Match the base model. If you fine-tune Llama-3.1-Instruct, use its template. If you fine-tune a base (non-instruct) model, you’re inventing the template — make sure your inference path uses the same one.
  3. Compute loss on assistant tokens only. TRL’s SFTTrainer has a DataCollatorForCompletionOnlyLM for this. Otherwise the model learns to predict the user’s tokens too — wasted capacity at best, leakage at worst.

C. Tooling Tour

Three on-ramps from easiest to most flexible

Option 1 — OpenAI / Hosted FT API

The fastest path. Upload a JSONL file, get a fine-tuned model ID back.

from openai import OpenAI
client = OpenAI()

# 1. Upload your dataset
training_file = client.files.create(
    file=open("data.jsonl", "rb"),
    purpose="fine-tune"
)

# 2. Kick off the job
job = client.fine_tuning.jobs.create(
    training_file=training_file.id,
    model="gpt-4o-mini-2024-07-18",
    hyperparameters={"n_epochs": 3}
)

# 3. Wait, then call your model
# response = client.chat.completions.create(model=job.fine_tuned_model, ...)
  • Pros: zero infra, integrated billing, evaluation hooks built in.
  • Cons: locked into the provider’s model family, model is not portable, per-token inference price is 2-4× base model.

Option 2 — HuggingFace TRL (DIY Open Source)

from trl import SFTTrainer, SFTConfig
from transformers import AutoTokenizer, AutoModelForCausalLM
from peft import LoraConfig

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.2-3B-Instruct")
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.2-3B-Instruct")

lora_config = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"])

trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=train_ds,
    eval_dataset=val_ds,
    peft_config=lora_config,
    args=SFTConfig(output_dir="./out", num_train_epochs=3, per_device_train_batch_size=4),
)

trainer.train()
trainer.save_model("./my-adapter")
  • Pros: full control, runs on any open model, adapters are portable.
  • Cons: you own the GPU procurement and the eval loop.

Realistic hyperparameter ranges

  • learning_rate: 2e-4 for LoRA, 1e-5 to 5e-5 for full fine-tuning. (LoRA tolerates a higher LR because it touches fewer weights.)
  • num_train_epochs: 1–3 for typical 1K–10K datasets. More than 3 usually means overfitting.
  • per_device_train_batch_size: as large as VRAM allows. Use gradient_accumulation_steps to simulate bigger effective batches.
  • warmup_ratio=0.03 is a safe default — prevents early-step instability.

Option 3 — Managed Open-Model Platforms

Together AI, Fireworks, Modal, Replicate — they run TRL for you on rented GPUs.

Provider Niche
Together AI LoRA on Llama / Mistral family; per-token billing on the result
Fireworks Fast inference + fine-tuning combined
Modal Bring-your-own-script serverless GPU (most flexible)
Replicate Easiest UI; good for prototyping

How to choose

Hosted FT API for prototypes and locked-in stacks. TRL + your GPU for production on open weights. Managed platform when you want open-weight flexibility without GPU procurement.

D. Evaluation & Overfitting

How to know if the training run actually helped

The Loss Curve is Not the Answer

Training loss going down ≠ model getting better

A 0.01 training loss with a 2.3 validation loss means you’ve memorized the training set. That’s overfitting, not learning.

What to watch:

Signal Meaning
Train loss ↓, val loss ↓ Healthy learning — keep going
Train loss ↓, val loss ↑ Overfitting — stop, or add regularization
Train loss flat Wrong learning rate or unteachable task
Both loss flat near zero Dataset too easy or too small

The Other Failure: Catastrophic Forgetting

A model can ace your task and get measurably worse at everything else.

What it looks like

You fine-tune a chat model for legal-document summarization. The summaries are perfect. Then a user asks “What’s the capital of France?” — and the model writes a legal disclaimer. You taught it your style; you also taught it to only answer like that.

Why it happens: fine-tuning shifts the weight distribution. Behaviors not reinforced by your dataset drift away. The smaller the dataset and the higher the learning rate, the worse it gets.

Mitigations:

Lever Effect
Use LoRA, not full FT Limits how far weights can move
Smaller learning rate, fewer epochs Less drift per step
Mix in general data (e.g., 10% OASST or your model’s own outputs) Anchors general capability
Eval on general prompts, not just task prompts You can’t fix what you don’t measure

The general-capability eval bucket

Your held-out test set should have two regions: on-task prompts (does it do the new thing?) and off-task prompts (does it still do the old things?). Report both numbers, always.

Task-Level Eval Matters More

Loss is a proxy. The real question is: does the model produce better outputs on a held-out set of real-world prompts?

# A minimum-viable eval harness
def evaluate(model, eval_set):
    scores = []
    for example in eval_set:
        prediction = model.generate(example["prompt"])
        scores.append(grade(prediction, example["reference"]))
    return sum(scores) / len(scores)

# `grade` can be:
#  - Exact match (for classification / extraction)
#  - BLEU / ROUGE (for translation / summarization — weak signal)
#  - LLM-as-judge (Module 03 §1) for free-form quality
#  - Custom rule-based scorer (your domain)

Always compare against the base model

Report (fine-tuned score) vs (base-model + best prompt score) on the same eval set. If fine-tuning doesn’t beat a well-prompted base, ship the prompt.

E. QLoRA Preview

A bridge to the next session

The Memory Wall

A 7B model in FP16 = ~14 GB just for weights. Add gradients, optimizer state, and activations → ~80 GB VRAM for full SFT. That’s an A100/H100 minimum.

LoRA cuts this by only updating adapters — gradients & optimizer state shrink ~100×.

QLoRA cuts it further by also storing the base model itself in 4-bit precision during training. Same 7B model now fits in ~6 GB VRAM. Runs on a consumer 24 GB GPU comfortably.

Why this matters for the curriculum

QLoRA = LoRA + quantized base model. Model Weight Quantization unpacks the quantization side: what 4-bit precision means, when accuracy suffers, and why this technique unlocks local fine-tuning on a laptop GPU.

F. Wrap-up

Key Takeaways

  1. Three methods, one decision tree — SFT for format, DPO for preference, LoRA/QLoRA for VRAM efficiency.
  2. Dataset is 90% of the project. 500 great examples beat 50,000 noisy ones.
  3. Build the eval first. Without a held-out test set, you have no idea if training helped.
  4. Hosted FT API is the fastest on-ramp; TRL + LoRA is the production sweet spot for open models.
  5. Overfitting is the default failure mode. Watch the val-loss gap, not training loss alone.
  6. QLoRA = LoRA + 4-bit base model. Makes fine-tuning runnable on a single consumer GPU — and is the bridge to Model Weight Quantization.
